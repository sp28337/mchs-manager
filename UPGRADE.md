# Переезд на 3.0: сервер синхронизации

Пошаговое руководство для владельца `grafik13.ru`. Проведёт от нынешнего
состояния (статический сайт, 2.18.0) до работающей синхронизации между
устройствами.

Соседние документы: [`DEPLOYMENT.md`](DEPLOYMENT.md) — про выкладку сайта,
[`deploy/README.md`](deploy/README.md) — справочник по серверу (состав,
резервные копии, неполадки), [`docs/legal/internal/README.md`](docs/legal/internal/README.md)
— что подписать до начала обработки персональных данных.

---

## 0. Что произойдёт и чего не произойдёт

**Что появится.** Рядом с сайтом встанет сервер: аккаунт по адресу почты,
копия графиков между устройствами, страницы политики и согласия.

**Чего не произойдёт.** Приложение не изменится для тех, кто аккаунт не
заведёт: расчёт по-прежнему в браузере, данные по-прежнему в `localStorage`,
файлы открываются как открывались. Учётная запись добровольна и ничего не
забирает.

**Главное про порядок.** Синхронизация включается **последней** — после
того, как сервер поднят, документы опубликованы и подано уведомление в
Роскомнадзор. До этого сайт собирается без неё: ни экрана входа, ни единого
обращения к серверу. Нарушить этот порядок — значит начать обработку
персональных данных до публикации политики (ч. 2 ст. 18.1 152-ФЗ) и до
уведомления (ст. 22).

### Карта пути

| Этап | Шаги | Сколько займёт | Можно ли отложить |
|---|---|---|---|
| Подготовка | 1–2 | 20 мин | нет |
| Сервер | 3–8 | 40–60 мин | нет |
| Выкладка | 9–11 | 20 мин | нет |
| Проверка | 12–13 | 20 мин | нет |
| Документы и закон | 14 | от суток (ждём РКН) | **нет: до включения** |
| Включение | 15–16 | 15 мин | да, хоть через месяц |

Этапы 1–13 ничего не меняют для людей на сайте: сервер стоит и отвечает, а
приложение о нём не знает. Это нарочно — так можно спокойно проверить всё,
не торопясь с юридической частью.

### Что понадобится

* **Сервер:** российский VPS, 2 ГБ памяти, 20 ГБ диска, Debian 13 или
  Ubuntu 24.04. Можно тот же, где лежит сайт, — так и задумано.
* **Доступы:** `ssh` на сервер с правами `sudo`; доступ к настройкам
  репозитория на GitHub; доступ к DNS домена.
* **На своей машине:** `age` (`apt install age` или `brew install age`),
  `ssh`, `docker` — для ежемесячной проверки копий.
* **Время:** два-три часа на всё, кроме ожидания Роскомнадзора.

## 1. Секреты и ключи — на своей машине

Делается **не на сервере**: закрытый ключ резервных копий на сервере лежать
не должен, иначе взломавший сервер получит и копии, и ключ к ним.

```bash
# Ключ, которым шифруются резервные копии базы
mkdir -p ~/.config/grafik13
age-keygen -o ~/.config/grafik13/backup-key.txt
chmod 600 ~/.config/grafik13/backup-key.txt
cat ~/.config/grafik13/backup-key.txt
```

В выводе строка `# public key: age1...` — это **открытый** ключ, он поедет
на сервер. Строка `AGE-SECRET-KEY-...` — **закрытый**, он остаётся у вас.

Дальше три секрета приложения:

```bash
openssl rand -base64 48   # GRAFIK_PEPPER
openssl rand -base64 48   # GRAFIK_JWT_SECRET
openssl rand -base64 36   # пароль базы
```

**Запишите всё это в менеджер паролей сразу.** Отдельно отметьте:

| Что | Если потерять |
|---|---|
| Закрытый ключ `age` | все резервные копии превращаются в мусор |
| `GRAFIK_PEPPER` | не войдёт никто, и восстановление по ключу не поможет: перец участвует в проверке пароля |
| Пароль базы | лечится переустановкой пароля в контейнере, не смертельно |
| `GRAFIK_JWT_SECRET` | лечится заменой: всех разлогинит, и только |

Перец и закрытый ключ копий храните **вместе и вне сервера**: копия базы
без перца бесполезна.

## 2. Проверить, что сайт выкладывается как раньше

Прежде чем менять что-то на сервере, убедитесь, что нынешняя выкладка
работает: иначе потом будет не понять, что сломалось.

```bash
curl -s https://grafik13.ru/robots.txt | head -3
```

Переменные и секреты GitHub для сайта должны быть на месте (Settings →
Secrets and variables → Actions): `SITE_URL`, `DEPLOY_ROOT`, `SSH_HOST`,
`SSH_USER`, `SSH_PRIVATE_KEY`, `SSH_KNOWN_HOSTS`, при нестандартном порте —
`SSH_PORT`.

## 3. Пакеты на сервере

```bash
ssh ваш-сервер
sudo apt update
sudo apt install -y docker.io docker-compose-v2 age nftables fail2ban postfix rsync curl
```

`postfix` при установке спросит тип — выберите **Internet Site**, имя
системы — `grafik13.ru`.

Пользователю, от которого идёт выкладка, нужен доступ к docker:

```bash
sudo usermod -aG docker ВАШ_ПОЛЬЗОВАТЕЛЬ
# перезайти по ssh, чтобы группа применилась
docker ps          # должно работать без sudo
```

## 5. Файлы окружения — поле за полем

### 5.1. `/opt/grafik13/postgres.env` — пароль базы

```bash
sudo tee /opt/grafik13/postgres.env > /dev/null <<'EOF'
POSTGRES_PASSWORD=ПАРОЛЬ_БАЗЫ_ИЗ_ШАГА_1
EOF
sudo chmod 600 /opt/grafik13/postgres.env
```

Файл читает сам PostgreSQL при **первом** запуске: пароль запечётся в том с
данными. Поменять его потом можно только через `ALTER USER` внутри
контейнера — учтите, если захочется «просто поправить файл».

### 5.2. `/opt/grafik13/api.env` — приложение

Возьмите за основу [`deploy/env.prod.example`](deploy/env.prod.example) и
заполните. Поле за полем:

| Переменная | Что вписать | Откуда взять | Что будет, если ошибиться |
|---|---|---|---|
| `GRAFIK_ENV` | `prod` | — | при `dev` откроются `/docs` и включится CORS |
| `GRAFIK_LOG_LEVEL` | `INFO` | — | `DEBUG` зальёт журнал подробностями |
| `GRAFIK_DATABASE_URL` | `postgresql+psycopg://grafik:ПАРОЛЬ@postgres:5432/grafik` | пароль из 5.1 | приложение не стартует, `/readyz` отвечает 503 |
| `GRAFIK_WORKERS` | `1` | — | при большем числе предел обращений делится между процессами |
| `GRAFIK_TRUSTED_PROXIES` | `172.28.0.1` | шлюз сети из `compose.prod.yml` | в журнале окажется адрес шлюза вместо адреса человека, и защита от перебора перестанет различать людей |
| `GRAFIK_PEPPER` | длинная строка из шага 1 | `openssl rand -base64 48` | приложение не стартует (проверка при старте); смена позже — никто не войдёт |
| `GRAFIK_JWT_SECRET` | другая длинная строка | там же | то же при старте; смена позже — всех разлогинит |
| `GRAFIK_ACCESS_TTL` | `900` | — | дольше живущий украденный токен |
| `GRAFIK_REFRESH_TTL_DAYS` | `30` | — | как часто придётся входить заново |
| `GRAFIK_LINK_TTL_HOURS` | `24` | — | срок жизни ссылки из письма |
| `GRAFIK_SMTP_HOST` | `172.28.0.1` | шлюз сети | письма не уйдут: регистрация завершится, но адрес не подтвердить |
| `GRAFIK_SMTP_PORT` | `25` | — | то же |
| `GRAFIK_SMTP_TLS` | `false` | — | канал не покидает машину, шифровать нечего |
| `GRAFIK_SMTP_USER` / `GRAFIK_SMTP_PASSWORD` | пусто | — | свой postfix их не спрашивает |
| `GRAFIK_MAIL_FROM` | `График 1 3 <noreply@grafik13.ru>` | — | письма уйдут от непонятного отправителя |
| `GRAFIK_PUBLIC_URL` | `https://grafik13.ru` | — | ссылки в письмах поведут не туда |

```bash
sudo nano /opt/grafik13/api.env
sudo chmod 600 /opt/grafik13/api.env
```

**Пустая строка `GRAFIK_SMTP_HOST=` отключает отправку писем вовсе** — так
можно поднять сервер до настройки почты: регистрация пройдёт, письмо не
уйдёт, в журнале останется запись. Для проверки это удобно, для боевой
работы — нет.

### 5.3. `/etc/grafik13/backup-recipients.txt` — кому шифровать копии

```bash
echo 'age1ВАШ_ОТКРЫТЫЙ_КЛЮЧ' | sudo tee /etc/grafik13/backup-recipients.txt
sudo chmod 600 /etc/grafik13/backup-recipients.txt
```

### 5.4. `/etc/grafik13/alerts.env` — куда писать о сбоях

```bash
printf 'ALERT_TO=вы@example.org\n' | sudo tee /etc/grafik13/alerts.env
sudo chmod 600 /etc/grafik13/alerts.env
```

Сюда придёт письмо, если ночная резервная копия не сделается. Без этого
файла задача просто промолчит — а молча падающая копия и есть самая частая
причина, по которой копий не оказывается в нужный день.

### 5.5. `/opt/grafik13/.env` — тег образа

Этот файл **пишет выкладка** (туда попадает короткий хэш коммита). Руками
его трогать не надо; он упомянут здесь, чтобы вы знали, откуда он взялся и
что `.env.previous` рядом — это откат.

## 6. Почта

В `/etc/postfix/main.cf`:

```
inet_interfaces = all
mynetworks = 127.0.0.0/8 [::1]/128 172.28.0.0/24
```

```bash
sudo systemctl restart postfix
```

`inet_interfaces = all`, а не адрес шлюза: интерфейс docker-сети создаётся
позже самим docker, и postfix при загрузке машины на нём просто не
поднимется. Снаружи 25-й порт закроет межсетевой экран (шаг 7).

**Чтобы письма доходили,** нужны три записи вне сервера:

| Запись | Где заводится | Зачем |
|---|---|---|
| PTR (обратная) на `grafik13.ru` | панель хостинг-провайдера | без неё письмо почти наверняка в спаме |
| SPF: `v=spf1 a mx -all` | DNS домена | то же |
| DKIM (`opendkim`) | сервер + DNS | то же |

Без них регистрация будет формально работать, но человек не получит письма
с подтверждением.

## 7. Межсетевой экран и fail2ban

```bash
# из каталога репозитория на своей машине
scp deploy/nftables.conf ваш-сервер:/tmp/
scp deploy/fail2ban-jail.local ваш-сервер:/tmp/

# на сервере
sudo cp /tmp/nftables.conf /etc/nftables.conf
sudo nft -c -f /etc/nftables.conf     # сперва проверить
sudo systemctl enable --now nftables

sudo cp /tmp/fail2ban-jail.local /etc/fail2ban/jail.local
sudo systemctl enable --now fail2ban
sudo fail2ban-client status sshd
```

Открытыми остаются три порта: 22, 80, 443. API наружу не смотрит вовсе.

> **Если на сервере уже настроен `ufw`** — используйте что-то одно. Два
> межсетевых экрана хуже одного: правила складываются неочевидно.

## 8. nginx: прокси для API

Настройка сайта в репозитории уже содержит блок `location ^~ /api/`.

```bash
# со своей машины
scp deploy/nginx-site.conf ваш-сервер:/tmp/
scp deploy/nginx-security-headers.conf ваш-сервер:/tmp/

# на сервере
sudo cp /tmp/nginx-site.conf /etc/nginx/sites-available/grafik13.ru
sudo cp /tmp/nginx-security-headers.conf /etc/nginx/snippets/security-headers.conf
sudo nginx -t && sudo systemctl reload nginx
```

`nginx -t` обязателен: опечатка в блоке прокси уронит и сайт.

## 10. Выложить новую версию

Ветка с работой — `claude/project-review-cd-fix-du8rix`. Влейте её в `main`
(pull request или прямым слиянием — как привычнее).

После пуша в `main` запустятся:

| Workflow | Что делает |
|---|---|
| **CI** | проверки и сборка сайта → артефакт |
| **CD** | раскладывает сайт по SSH, проверяет пять страниц и `robots.txt` |
| **API** | линтеры, типы, миграции вверх-вниз, тесты, сборка образа → артефакт |
| **API CD** | привозит образ на сервер, применяет миграции, поднимает контейнеры, проверяет снаружи |

Следите за вкладкой Actions. **Первая выкладка API упадёт**, если на
сервере нет `api.env` или `postgres.env`, — так и задумано, сообщение будет
прямым.

После выкладки на сайте появятся страницы `/privacy`, `/consent` и
обновлённые `/terms` — пока **с оговоркой «проект документа»** и
подстановками вида `[фио оператора]`. Так и должно быть: документы
становятся действующими на шаге 14, и до тех пор ни один из них не выдаёт
себя за опубликованный.

### Если выкладка API не запустилась сама

Actions → **API CD** → Run workflow → в поле `run_id` укажите номер
запуска workflow «API», в котором собрался образ (его видно в адресной
строке того запуска).

## 11. Что происходит с базой (и как это проверить)

Отдельного «развёртывания базы» делать не нужно — выкладка делает всё сама,
но полезно понимать, что именно:

1. `docker compose up` поднимает контейнер `postgres` из образа
   `postgres:18.6-trixie`;
2. при первом запуске он создаёт кластер в томе `grafik13_pgdata` с
   пользователем `grafik`, базой `grafik` и паролем из `postgres.env`.
   Том монтируется в `/var/lib/postgresql`, а сами данные ложатся в
   подкаталог с номером выпуска — `/var/lib/postgresql/18/docker`: так
   устроен образ с версии 18, и так `pg_upgrade --link` потом не упрётся в
   границу монтирования;
3. `docker compose run --rm migrate` применяет миграции Alembic — таблицы
   появляются здесь;
4. контейнер `api` стартует и начинает отвечать.

Проверить руками:

```bash
cd /opt/grafik13

# что запущено
docker compose -f compose.prod.yml ps

# таблицы на месте
docker compose -f compose.prod.yml exec -T postgres \
  psql -U grafik -d grafik -c '\dt'

# на какой миграции схема
docker compose -f compose.prod.yml exec -T postgres \
  psql -U grafik -d grafik -c 'SELECT version_num FROM alembic_version'

# где лежат данные
docker volume inspect grafik13_pgdata --format '{{.Mountpoint}}'
```

Ожидаемые девять таблиц: `users`, `credentials`, `data_keys`, `blobs`,
`blob_revisions`, `refresh_tokens`, `one_time_tokens`, `consents`,
`audit_log`.

Если миграции нужно применить вручную (например, после восстановления из
копии):

```bash
docker compose -f compose.prod.yml run --rm migrate
```

## 12. Проверка «сервер жив»

```bash
# снаружи, через nginx
curl -s https://grafik13.ru/api/v1/healthz        # {"status":"ok","version":"0.1.0"}
curl -s https://grafik13.ru/api/v1/readyz         # {"status":"ready",...} — значит и база отвечает
curl -s https://grafik13.ru/api/v1/legal/documents | head -c 200

# на сервере
ss -ltnp | grep -E '8001|5432'    # 8001 только на 127.0.0.1, 5432 — пусто
docker compose -f /opt/grafik13/compose.prod.yml logs --tail 20 api
sudo nft list table inet grafik | head -20

# письмо из контейнера доходит до postfix
docker compose -f /opt/grafik13/compose.prod.yml exec api \
  python -c "import socket; socket.create_connection(('172.28.0.1', 25), 5); print('ок')"
```

В журнале приложения одна строка — один JSON, и в нём **нет** ни адресов
почты, ни блобов: человек обозначен идентификатором.

## 13. Расписания и первая резервная копия

```bash
# со своей машины
ssh ваш-сервер 'mkdir -p /tmp/systemd'
scp deploy/systemd/* ваш-сервер:/tmp/systemd/

# на сервере
sudo cp /tmp/systemd/* /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now grafik-gc.timer grafik-backup.timer grafik-backup-verify.timer
systemctl list-timers 'grafik-*'

# сделать копию прямо сейчас, не дожидаясь ночи
sudo /opt/grafik13/backup.sh
sudo /opt/grafik13/backup-verify.sh
ls -l /var/backups/grafik13/
```

| Таймер | Когда | Что делает |
|---|---|---|
| `grafik-gc.timer` | 03:17 ± 15 мин | исполняет сроки хранения: надгробия, версии, журнал событий, протухшие токены, брошенные регистрации |
| `grafik-backup.timer` | 02:40 ± 20 мин | резервная копия, зашифрованная вашим открытым ключом; хранит 30 дней |
| `grafik-backup-verify.timer` | 03:40 ± 10 мин | проверяет, что копия свежая, не пустая и зашифрована |

### Проверить, что копия разворачивается — на своей машине

Это единственная проверка, которую нельзя сделать на сервере: закрытого
ключа там нет.

```bash
scp ваш-сервер:/var/backups/grafik13/grafik13-*.dump.age ./
GRAFIK_BACKUP_KEY=~/.config/grafik13/backup-key.txt \
  ./deploy/restore-check.sh grafik13-ГГГГММДД-ЧЧММСС.dump.age
```

Скрипт поднимет одноразовый PostgreSQL, восстановит в него копию, проверит
таблицы и покажет число строк. Повторяйте раз в месяц — непроверенная копия
это не копия, а надежда.

## 14. Документы и закон — до включения

**Это обязательный этап, а не формальность.** Обработка персональных данных
не может начаться раньше, чем опубликована политика и подано уведомление.

Полный чек-лист — в [`docs/legal/internal/README.md`](docs/legal/internal/README.md),
раздел «Чек-лист перед началом обработки». Коротко:

1. **Сверить нормы** по таблице в том же файле: часть текстов приводилась
   по открытым публикациям, потому что официальные источники из среды
   разработки недоступны.
2. **Проверить статус нового приказа ФСТЭК** взамен приказа № 21 (проект от
   24.07.2026). Вступил в силу — перечень мер переделывается, и проводится
   оценка «уровня зрелости».
3. **Показать пакет юристу** по персональным данным — вопросы перечислены
   там же, главный из них про сведения о здоровье.
4. **Заполнить подстановки** в документах: `{{ФИО_ОПЕРАТОРА}}`,
   `{{ПОЧТОВЫЙ_АДРЕС}}`, `{{ДАТА_ВСТУПЛЕНИЯ}}` — в `docs/legal/*.md` и
   `docs/legal/internal/*.md`; выставить `status: published` и
   `effective_from`.
5. **Пересобрать манифест и проверить:**

   ```bash
   node scripts/legal.mjs write
   node scripts/legal.mjs
   ```

6. **Скопировать опубликованные редакции** в `docs/legal/archive/<id>/<версия>.md`.
7. **Подписать внутренние документы** (бумага или электронная подпись),
   завести журнал обращений и журнал внутреннего контроля по формам.
8. **Подать уведомление** об обработке персональных данных в Роскомнадзор —
   **до начала обработки** (ст. 22 152-ФЗ). Форму сверить на `rkn.gov.ru` в
   день подачи.
9. **Дождаться включения в реестр**, влить правки документов в `main` и
   убедиться, что страницы `/privacy`, `/consent`, `/terms` открываются уже
   без оговорки «проект документа».

## 15. Включить синхронизацию

Один переключатель:

**GitHub → Settings → Secrets and variables → Actions → Variables → New
repository variable:**

```
Name:  SYNC_ENABLED
Value: 1
```

Переменная действует на **сборке**, поэтому сайт надо пересобрать и
выложить. Выкладка запускается пушем в `main` — и удобнее всего совместить
её с выпуском:

```bash
# в CHANGELOG.md: «Не выпущено» → «## [3.0.0] — ГГГГ-ММ-ДД», ниже новый
# пустой раздел «Не выпущено», внизу ссылка на сравнение версий
git commit -am "Выпуск 3.0.0: синхронизация между устройствами"
git push origin main
```

Пуш запустит **CI** (сборка уже с переменной) и следом **CD**.

> Ручной запуск CI из вкладки Actions соберёт сайт, но **не выложит**: CD
> слушает только сборки, вызванные пушем в `main` (`cd.yml`, условие
> `workflow_run.event == 'push'`). Если выпускать нечего, а пересобрать
> надо — подойдёт пустой коммит:
> `git commit --allow-empty -m "Пересборка: включение синхронизации"`.

Что изменится на сайте:

* на посадочной появится плашка «Нужно на телефоне и на компьютере»;
* в подвале рабочего экрана — строка «Синхронизация между устройствами»;
* страница `/account` начнёт работать по-настоящему.

**Выключить обратно** можно так же: удалить переменную (или поставить
пустое значение) и пересобрать. Сервер при этом продолжит работать, а
приложение перестанет к нему обращаться — у тех, кто уже завёл аккаунт,
данные останутся и в браузере, и на сервере.

## 16. Приёмка: проверить на двух устройствах

Это же — оценка эффективности мер до ввода системы в эксплуатацию (п. 4
ч. 2 ст. 19 152-ФЗ), и её результат записывается в журнал внутреннего
контроля.

1. Телефон: открыть `/account`, зарегистрироваться, **записать ключ
   восстановления на бумагу**.
2. Получить письмо, перейти по ссылке — адрес подтверждён.
3. Телефон: внести что-нибудь в график (отпуск, вызов).
4. Компьютер: войти тем же адресом и паролем — график приезжает сам.
5. Компьютер: поправить день. Телефон: обновить страницу — правка на месте.
6. Отключить сеть на телефоне, поправить день, включить сеть — правка
   уезжает сама.
7. Поправить **один и тот же** день на обоих устройствах, пока второе без
   сети, — появится окно с выбором, какую правку оставить.
8. Сменить пароль на компьютере — на телефоне попросит войти заново.
9. «Выгрузить всё, что обо мне есть» — файл скачивается и открывается.
10. «Удалить учётную запись» — проверить, что в базе ничего не осталось:

    ```bash
    docker compose -f /opt/grafik13/compose.prod.yml exec -T postgres \
      psql -U grafik -d grafik -c \
      "SELECT (SELECT count(*) FROM users) AS аккаунтов,
              (SELECT count(*) FROM blobs) AS записей,
              (SELECT count(*) FROM audit_log WHERE event = 'account.deleted') AS удалений"
    ```

    Ожидается: аккаунтов 0, записей 0, удалений 1 — последняя строка и есть
    подтверждение уничтожения.

11. Записать результат в журнал внутреннего контроля.
12. Выпустить версию: раздел «Не выпущено» в `CHANGELOG.md` → `## [3.0.0] —
    дата`, тег `v3.0.0`, пуш тега.

## Если что-то пошло не так

| Признак | Причина чаще всего | Что делать |
|---|---|---|
| Выкладка API упала на «сервер не подготовлен» | нет `api.env` или `postgres.env` | шаг 5 |
| `502` на `/api/...`, сайт работает | контейнер `api` не поднялся | `docker compose logs api`; при слабом секрете приложение не стартует намеренно |
| `/readyz` отвечает 503 | база не поднялась или не тот пароль | `docker compose ps`, журнал контейнера `postgres` |
| Письма не приходят | postfix не принимает из контейнера, или нет PTR/SPF/DKIM | шаг 6 |
| В журнале адрес `172.28.0.1` вместо адреса человека | не задан `GRAFIK_TRUSTED_PROXIES` | шаг 5.2, перезапустить `api` |
| `429` у человека на ровном месте | `GRAFIK_WORKERS` больше единицы | вернуть `1` |
| Сайт собрался, а синхронизации нет | переменная `SYNC_ENABLED` не задана или сборка старая | шаг 15, пересобрать |
| `postgres` не стартует: «in 18+, these Docker images are configured to store database data …», «(unused mount/volume)» | том смонтирован по старому пути `/var/lib/postgresql/data` — так было в составе до 14.10.2026 | обновить `compose.prod.yml` (том идёт в `/var/lib/postgresql`); если база ещё пустая — убрать том: `docker compose -f compose.prod.yml down -v`. С данными — сначала снять копию `backup.sh`, потом пересоздавать |
| Нужно откатить API | — | `cd /opt/grafik13 && cp .env.previous .env && docker compose -f compose.prod.yml up -d api` |
| Нужно откатить сайт | — | переключить симлинк `current` на прошлый выпуск (`DEPLOYMENT.md`) |

Полный справочник по серверу — [`deploy/README.md`](deploy/README.md).

## Приложение: попробовать у себя до сервера

Если хочется посмотреть на всё до переезда — на своей машине с docker:

```bash
make up          # postgres + api + ловушка писем
# API      http://127.0.0.1:8000/api/v1/healthz
# Письма   http://127.0.0.1:8025

# в другом окне, в корне репозитория
echo 'NEXT_PUBLIC_SYNC_ENABLED=1' >> .env.local
echo 'NEXT_PUBLIC_API_URL=http://localhost:8000/api/v1' >> .env.local
pnpm dev
```

Открывать строго `http://localhost:3000`, а не `127.0.0.1:3000`: для
браузера это разные узлы, и cookie сессии с `SameSite=Strict` на второй не
уйдёт, а CORS при разработке разрешён ровно для `localhost:3000`. По той же
причине и ссылки в письмах ведут на `localhost`.

Письма (подтверждение адреса, восстановление) ловит `mailpit` на
`http://127.0.0.1:8025` — настоящая почта при этом никуда не уходит; его
собственный адрес роли не играет, по ссылке из письма браузер уйдёт на
`localhost:3000`.

Что посмотреть: `/account` — вход и регистрация (пароль от восьми знаков,
отметка согласия, после регистрации — ключ восстановления), `/calculator` —
строка состояния в подвале, `/privacy`, `/consent`, `/terms` — документы с
оговоркой «проект документа».

Остановить: `make down`. Данные останутся в томе; удалить их целиком —
`docker compose down -v`.

> **Если `postgres` не поднимается** и пишет про «unused mount/volume» —
> значит остался том от состава, где он монтировался в
> `/var/lib/postgresql/data` (так было до 14.10.2026). Лечится одной
> командой, данных для разработки не жалко:
>
> ```bash
> docker compose down -v && make up
> ```
