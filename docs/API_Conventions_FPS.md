# REST API — конвенции и обзор
## Система расчёта служебного времени сотрудников ФПС России

Полная спецификация — файл `openapi.yaml` (OpenAPI 3.1.1, синтаксис сверен с Context7, `/websites/spec_openapis_oas_v3_1_0`). Backend не пишется — только контракт. Этот файл объясняет решения, которые в самом YAML выражены неявно (через структуру, а не прозу).

---

## 1. Версионирование API

**Схема:** версия в пути — `/api/v1/...`. Причина выбора именно URI-версионирования, а не заголовка (`Accept-Version`) или content-negotiation:
- Модульный монолит (см. Architecture) уже даёт по одному Presentation-адаптеру на модуль — версия в пути позволяет версionировать **каждый модуль независимо** (`/api/v1/time-accounting/...` может дожить до v2, пока `/api/v1/legal-rules/...` остаётся на v1), не требуя единой версии для всего приложения сразу.
- Явно видна в логах, легко фильтруется на уровне API Gateway/Load Balancer без разбора заголовков.

**Политика изменений:**
| Тип изменения | Требует новой версии? |
|---|---|
| Добавление необязательного поля в ответ | Нет |
| Добавление нового необязательного query-параметра | Нет |
| Добавление нового endpoint | Нет (в рамках той же версии) |
| Удаление/переименование поля, изменение типа поля | Да |
| Изменение семантики существующего кода ошибки | Да |
| Изменение обязательности поля запроса (opt → required) | Да |

**Устаревание:** endpoint, помечаемый к выводу из эксплуатации, возвращает заголовки `Deprecation: true` и `Sunset: <RFC 1123 date>` не менее чем за 90 дней до отключения — параллельно с версией-заменой, доступной уже на момент объявления `Deprecation`.

## 2. Авторизация

**Модель:** OAuth2 + JWT (Bearer), `securityScheme` типа `http`/`bearer`/`JWT` (синтаксис подтверждён Context7). Токен выдаётся внешним Identity Provider (вне зоны ответственности данного API) и содержит:
- `sub` — идентификатор пользователя;
- `roles` — массив ролей из перечня SRS (раздел 3): `employee`, `shift_commander`, `timekeeper`, `unit_commander`, `hr_specialist`, `finance_specialist`, `legal_officer`, `regional_commander`, `system_admin`, `auditor`;
- `unit_scope` — идентификатор подразделения (для ограничения видимости данных ролей `unit_commander`/`timekeeper` только своим подразделением, см. Architecture, разд. 10 п.2).

**Правило авторизации на уровне ресурса (Row-Level, не только Endpoint-Level):**
- Роль **`employee`** может читать только ресурсы, где `employeeId` в пути/параметре совпадает с `sub` токена (см. Domain: «сотрудник видит только свои данные»).
- Роль **`unit_commander`**/**`timekeeper`** может читать/писать ресурсы, чей `unitId` входит в `unit_scope` токена.
- Роль **`legal_officer`** — единственная, имеющая доступ на запись к `/api/v1/legal-rules/**` (публикация версий правил).
- Роль **`auditor`** — доступ только на чтение (`GET`) ко всем модулям, без исключений.

Это выражено в спецификации через `security` на уровне каждой операции (не глобально) плюс scope-проверка, которая **не** выразима декларативно в OpenAPI (OpenAPI описывает *какая роль имеет доступ к операции*, но не *к какой именно записи* — это уже относится к домену Application-слоя, см. Architecture, `BuildingBlocks/Application` pipeline).

**Схема токена (пример полезной нагрузки, не эндпоинт получения токена — он вне зоны ответственности данного API, лежит на Identity Provider):**
```json
{
  "sub": "3f2a1c4e-...",
  "roles": ["timekeeper"],
  "unit_scope": ["b7e0..."],
  "exp": 1751328000
}
```

## 3. Модель ошибок

**Формат:** RFC 7807 (`application/problem+json`) — единый для всех модулей, каждая операция ссылается на общие `components/responses`.

```json
{
  "type": "https://api.fps-timekeeping.gov.ru/errors/rule-version-not-found",
  "title": "Не найдена действующая версия правила",
  "status": 422,
  "detail": "Для категории 'norm_calculation' и заданного scope на дату 2026-01-15 не найдено опубликованной версии правила.",
  "instance": "/api/v1/time-accounting/timesheets/9c11.../events",
  "traceId": "b3a1e2..."
}
```

**Единый каталог кодов состояния и когда они используются:**

| HTTP-статус | Когда | `type` (пример) |
|---|---|---|
| `400 Bad Request` | Некорректная форма запроса (не проходит JSON Schema валидацию тела/параметров) | `.../errors/validation-failed` |
| `401 Unauthorized` | Отсутствует/просрочен токен | `.../errors/unauthenticated` |
| `403 Forbidden` | Токен валиден, но роль/scope не даёт доступа к ресурсу | `.../errors/forbidden` |
| `404 Not Found` | Ресурс с данным id не существует | `.../errors/not-found` |
| `409 Conflict` | Нарушение уникальности/пересечения (например, пересекающиеся интервалы смен — прямое отражение `EXCLUDE`-ограничений из логической модели PostgreSQL) | `.../errors/overlapping-interval` |
| `422 Unprocessable Entity` | Синтаксически верный запрос нарушает бизнес-инвариант домена (например, привлечение сверх нормы без `overtimeOrderId`, попытка списать ДДО сверх остатка) | `.../errors/domain-invariant-violation` |
| `423 Locked` | Попытка изменить неизменяемый ресурс (`Timesheet`/`CompensationCase` в статусе `approved`/`finalized`, `RuleVersion` со статусом `published`) | `.../errors/immutable-resource` |
| `429 Too Many Requests` | Превышен лимит запросов | `.../errors/rate-limited` |
| `500 Internal Server Error` | Непредвиденная ошибка | `.../errors/internal` |

Каждая ошибка **обязана** нести `traceId`, сквозной для корреляции с `audit.audit_log` (см. логическую модель PostgreSQL) — без него невозможно связать отклонённый запрос с записью аудита.

## 4. Валидация

Два независимых уровня, которые нельзя путать (это прямое отражение разделения «форма запроса» / «бизнес-инвариант» из документа «Движок расчёта», Алгоритм В и далее):

1. **Валидация формы (`400`)** — выражена декларативно в OpenAPI через JSON Schema: `required`, `type`, `format` (`date`, `date-time`, `uuid`), `enum`, `minLength`/`maxLength`, `pattern`, `minimum`/`maximum`. Выполняется до вызова Application-слоя.
2. **Валидация бизнес-инварианта (`409`/`422`/`423`)** — не выразима в OpenAPI-схеме (требует обращения к состоянию агрегата/БД — например, «пересекается ли эта смена с уже существующей», «утверждён ли Timesheet»). В спецификации отражена только *как возможный код ответа операции с описанием условия*, сама проверка — за пределами контракта.

**Пример декларативной валидации DTO (`RegisterActualShiftRequest`):**
- `startTime`, `endTime` — `format: date-time`, `endTime` строго позже `startTime` — последнее правило НЕ выразимо стандартной JSON Schema (нет операции сравнения двух полей) и указано в `description` поля как пояснение к бизнес-правилу, фактически проверяемому на уровне `422`.
- `employeeId` — `format: uuid`, обязателен.

## 5. Идемпотентность команд (важно для CQRS Command-эндпоинтов)

Все `POST`-операции, изменяющие состояние (регистрация факта, публикация версии правила, финализация компенсации), принимают заголовок `Idempotency-Key` (`uuid`, обязателен). Повторный вызов с тем же ключом в течение 24 часов возвращает **тот же** ответ, что и первый вызов, не порождая вторую запись — это защищает от дублирования при сетевых ретраях на клиенте, что особенно критично для операций, которые по инварианту не могут выполняться дважды (например, повторное списание ДДО).

## 6. Пагинация и фильтрация (единая конвенция для всех списковых `GET`)

- Параметры: `page` (целое, ≥1, по умолчанию 1), `pageSize` (целое, 1–200, по умолчанию 50).
- Ответ — конверт: `{ "items": [...], "page": 1, "pageSize": 50, "totalCount": 1234 }`.
- Фильтрация — через явные именованные query-параметры конкретного endpoint (`periodStart`, `periodEnd`, `unitId` и т.п.), без универсального `filter=`-DSL — ради читаемости контракта и совместимости с OpenAPI-валидацией параметров.

## 7. Соответствие модулям

Структура `paths` в `openapi.yaml` сгруппирована тегами один-в-один с модулями из документа Architecture: `LegalRules`, `Personnel`, `ServiceCalendar`, `Scheduling`, `TimeAccounting`, `Compensation`, `RestBalance`, `LeaveManagement`. Это не случайность — граница HTTP-тега воспроизводит границу bounded context, чтобы контракт не «протекал» через модули так, как это запрещено на уровне кода (Architecture, разд. 6–7).
