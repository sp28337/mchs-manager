# Domain Model (DDD)
## Предметная область: расчёт служебного времени сотрудников ФПС России

**Версия:** 0.1
**Тип документа:** Доменная модель (стратегический + тактический DDD-анализ)
**Явно вне области документа:** база данных, ORM, схемы хранения, API, транспортные протоколы, инфраструктура. Ниже описан исключительно **домен** — сущности, агрегаты, объекты-значения, инварианты и их связи, как они существуют независимо от способа хранения или доступа.

---

## 0. Ключевой архитектурный принцип домена

Домен строится **не вокруг сотрудника, а вокруг правила**. Правило — это первичный смысловой объект: оно существует независимо от того, к какому сотруднику применяется. Расчёт — это применение конкретной версии правила к фактам конкретного сотрудника за конкретный период.

```
NormativeDocument ──цитирует──▶ Rule (RuleVersion) ──применяется через──▶ Calculation
                                                                              │
                                                                       ссылается на
                                                                              ▼
                                                                          Employee
```

Это отражено в структуре модели: **Legal Rules & Calculation** — самостоятельный ограниченный контекст, от которого зависят все контексты, производящие расчёты (Time Accounting, Compensation, Leave Management, Scheduling), а не наоборот.

---

## 1. Стратегический анализ: Bounded Contexts

| Bounded Context | Тип (Core / Supporting / Generic) | Ответственность |
|---|---|---|
| **Legal Rules & Calculation** | **Core** | Формализованные версионированные правила расчёта норм, категорий времени и компенсаций; правило разрешения конфликтов при пересечении категорий |
| **Time Accounting** | **Core** | Фиксация фактического служебного времени, расчёт отклонений от нормы (табель) |
| **Scheduling** | Supporting | Планирование графиков дежурств/смен |
| **Compensation** | Supporting | Определение и фиксация формы и объёма компенсации по итогам периода |
| **Rest Balance** | Supporting | Учёт накопленных/использованных дополнительных суток отдыха |
| **Leave Management** | Supporting | Отпуска всех видов, отзыв из отпуска |
| **Personnel & Organization** | Generic | Сотрудники, должности, подразделения — потребляется всеми контекстами только по идентификатору |
| **Service Calendar** | Generic | Календарь рабочих/выходных/праздничных дней |

### 1.1 Context Map (связи между контекстами)

```
Personnel & Organization ──(Conformist, читают по ID)──▶  Scheduling
        │                                                      │
        │(Conformist)                                          │(Customer / Supplier)
        ▼                                                      ▼
   Time Accounting  ◀──(Open Host Service)── Legal Rules & Calculation
        │                                                      ▲
        │(Customer / Supplier)                                 │(Open Host Service)
        ▼                                                      │
   Compensation ───(Customer / Supplier)───▶ Rest Balance      │
        │                                                      │
        ▼                                                      │
   Leave Management ─────────(Open Host Service)────────────────┘
        │
        └──(Conformist, читает по ID)──▶ Personnel & Organization, Scheduling
```

**Правило связывания агрегатов (общее для всей модели):** ни один агрегат не хранит ссылку на объект другого агрегата целиком — только его идентификатор (`EmployeeId`, `PositionId`, `RuleVersionId`, `OrderId` и т.д.). Это обеспечивает независимую согласованность (consistency boundary) каждого агрегата и позволяет каждому bounded context эволюционировать независимо.

### 1.2 Единый язык (Ubiquitous Language) — ключевые термины
Термины идентичны используемым в SRS (Служебное время, Норма, Учётный период, Переработка, Недоработка, Ночное время, Дежурная смена, ДДО и т.д.) — сознательно не дублируются здесь полностью, см. SRS п. 1.4. Ниже вводятся только термины, специфичные для доменной (тактической) модели.

## 2. Bounded Context: Legal Rules & Calculation *(Core Domain)*

Это контекст, реализующий философию «Rule → Calculation → Employee». Он не знает о сотрудниках — он знает только о правилах и их формальном действии.

### 2.1 Агрегат `NormativeDocument` (Нормативный документ)

**Aggregate Root:** `NormativeDocument`

**Сущности внутри агрегата:**
- `Chapter` (Глава) — принадлежит документу, имеет порядковый номер.
- `Article` (Статья) — принадлежит главе.
- `Paragraph` (Пункт/часть статьи) — принадлежит статье; конечная адресуемая единица текста.

**Value Objects:**
- `DocumentIdentity` — {тип документа: ФЗ/Приказ/Постановление, регистрационный номер, дата принятия}.
- `DocumentValidityPeriod` — {дата вступления в силу, дата утраты силы (опционально)}.

**Инварианты:**
1. `DocumentIdentity` уникален в рамках всей модели — два документа с одинаковым типом+номером+датой существовать не могут.
2. Нумерация `Chapter → Article → Paragraph` уникальна и монотонна внутри документа (нельзя иметь два пункта с одинаковым адресом в одной версии документа).
3. `NormativeDocument` — только источник цитирования (readonly-текст с точки зрения расчётной логики). Сам по себе он **не является** правилом расчёта — правило порождается отдельно, документ лишь обосновывает его (см. `Rule.legalBasis`).
4. Правки в документ создают новую `DocumentValidityPeriod`, а не переписывают предыдущий текст — исторический текст неизменяем (требование восстанавливаемости расчётов за любой прошлый год).

---

### 2.2 Агрегат `Rule` (Правило расчёта)

**Aggregate Root:** `Rule` — представляет собой *идентичность* правила (например, «Норма служебного времени», «Классификация ночных часов», «Порядок разрешения конфликта категорий», «Коэффициент компенсации переработки»), которая сохраняется на протяжении всех редакций.

**Сущности внутри агрегата:**
- `RuleVersion` — конкретная, неизменяемая, датированная редакция правила. Один `Rule` содержит хронологию `RuleVersion`.

**Value Objects:**
- `RuleCategory` (enum) — `NormCalculation | NightHoursClassification | HolidayHoursClassification | OvertimeClassification | ConflictResolutionPolicy | CompensationCoefficient | LeaveEntitlement | MinimumRestPeriod`.
- `EffectivePeriod` — {validFrom, validTo (опционально открытый)} — период действия конкретной `RuleVersion`.
- `LegalBasis` — {ссылка на `NormativeDocument` + `Chapter`/`Article`/`Paragraph`} — обоснование правила; VO, не агрегат (документ цитируется, но не владеется правилом).
- `Scope` — {применимо к: категории условий службы / категории должностей / всем} — определяет область действия версии правила (например, отдельная норма для вредных условий).
- `FormulaDefinition` — формальное, декларативное описание способа вычисления (входные величины и порядок их сочетания), выраженное как данные, а не как исполняемый код — например, «результат = функция(WeeklyNorm, ServiceCalendar, Scope)». Формула — абстрактный value object уровня домена, конкретный синтаксис вычисления — предмет последующего проектирования, не хранения.

**Инварианты:**
1. Для одной и той же комбинации `(RuleCategory, Scope)` **не может существовать двух `RuleVersion` с пересекающимися `EffectivePeriod`** — на любую календарную дату действует ровно одна версия правила для данной области применения. Это ключевой инвариант, обеспечивающий детерминированный пересчёт за любой прошлый год.
2. `RuleVersion`, однажды опубликованная (переведённая в статус «Действует» или «Утратила силу»), **неизменяема**. Исправление ошибки в правиле порождает новую `RuleVersion` с новым `EffectivePeriod`, а не редактирование существующей.
3. Каждая `RuleVersion` обязана иметь непустой `LegalBasis` — правило без ссылки на нормативный акт не может быть опубликовано (правило не может существовать «само по себе», без легитимации).
4. `EffectivePeriod.validFrom` не может быть раньше `DocumentValidityPeriod.validFrom` документа, указанного в `LegalBasis` (правило не может действовать раньше своего правового основания).

---

### 2.3 Агрегат `ConflictResolutionPolicy` (Политика разрешения пересечения категорий)

**Aggregate Root:** `ConflictResolutionPolicy` — самостоятельный агрегат (несмотря на то, что концептуально это частный случай `Rule`, он выделен отдельно, так как имеет собственный жизненный цикл и структуру, отличную от вычислительных правил).

**Value Objects:**
- `CategoryPrecedenceList` — упорядоченный список `RuleCategory` (например: сначала классифицировать праздничные часы, затем ночные, затем определить переработку), гарантирующий отсутствие «задвоения» одного и того же часа в двух формах компенсации без правового основания.
- `EffectivePeriod` (как в 2.2).

**Инварианты:**
1. Список `CategoryPrecedenceList` не может содержать дублирующиеся категории.
2. Один и тот же календарный час, попадающий одновременно в несколько категорий, при применении политики должен быть отнесён к **точно определённому** набору категорий согласно порядку списка — политика обязана быть **полной функцией** (для любой комбинации категорий существует однозначный результат), а не частичной.

## 3. Bounded Context: Personnel & Organization *(Generic Subdomain)*

### 3.1 Агрегат `Employee` (Сотрудник)

**Aggregate Root:** `Employee`

**Сущности внутри агрегата:**
- `ServiceRecordEntry` — запись истории прохождения службы (назначение/перевод/присвоение звания) — исторический, только для чтения список, пополняемый.
- `SecondaryAssignment` — совмещение/совместительство (ст. 34 ФЗ-141): отдельная, ограниченная по времени должность, привязанная к основной занятости сотрудника, с собственной нормой.

**Value Objects:**
- `PersonalIdentity` — {ФИО, табельный номер} — табельный номер уникален и неизменяем.
- `Rank` — специальное звание.
- `SeniorityDuration` — {calendarYears, preferentialYears} — стаж в календарном и льготном исчислении.
- `ServiceConditionCategory` (enum) — `Normal | HazardousOrDangerous | Pedagogical`.
- `EmploymentStatus` (enum) — `Active | OnLeave | Sick | Suspended | Dismissed`.

**Инварианты:**
1. `PersonalIdentity.personnelNumber` уникален в рамках всей модели.
2. В любой момент времени у `Employee` **ровно одна** активная основная должность (`PositionId`, ссылка на агрегат `Position` по идентификатору) — совместительство или временное исполнение обязанностей моделируются отдельно (`SecondaryAssignment`), не подменяя основную должность.
3. Переходы `EmploymentStatus` подчиняются конечному автомату: `Active ⇄ OnLeave`, `Active ⇄ Sick`, `Active → Suspended → (Active | Dismissed)`, `* → Dismissed` (терминальное состояние, необратимо). Прямой переход `Dismissed → Active` запрещён — восстановление после увольнения создаёт новую сущность найма, а не откатывает статус.
4. `SecondaryAssignment` не может по своим временным границам полностью совпадать с периодом временной нетрудоспособности или отстранения по основной должности (нельзя нести обязанности по совмещаемой должности, будучи признанным нетрудоспособным).

---

### 3.2 Агрегат `Position` (Должность)

**Aggregate Root:** `Position`

**Value Objects:**
- `PositionCategory` (enum) — влияет на область применения правил из `Rule.Scope`.
- `DefaultRegimeType` (enum) — `FiveDayWeek | ShiftSchedule | TwentyFourHourDuty | Unstandardized`.
- `WeeklyNormReference` — не хранит число часов «жёстко», а хранит **ссылку на актуальное применимое `RuleVersion`** категории `NormCalculation` для данной `PositionCategory`/`ServiceConditionCategory` — число часов есть производная величина, а не атрибут должности (снова принцип «Rule → Calculation»).

**Инварианты:**
1. `Position` не может ссылаться на `RuleVersion`, чей `Scope` не покрывает `PositionCategory`/`ServiceConditionCategory` данной должности (нельзя присвоить норму, которая юридически на неё не распространяется).
2. Изменение `DefaultRegimeType` не переписывает историю уже утверждённых `DutySchedule` — влияет только на будущие периоды.

---

### 3.3 Агрегат `Unit` (Подразделение)

**Aggregate Root:** `Unit`

**Value Objects:**
- `UnitHierarchyPath` — материализованный путь в иерархии подразделений (для контроля отсутствия циклов).

**Инварианты:**
1. `Unit` имеет не более одного родителя; граф подразделений — дерево (ацикличность обязательна).
2. `Unit` не может быть удалено/расформировано, если на него ссылается хотя бы один `Employee` со статусом `Active` (перенос сотрудников — обязательное предварительное действие, инвариант защищает от «осиротевших» сотрудников).

## 4. Bounded Context: Service Calendar *(Generic Subdomain)*

### 4.1 Агрегат `ServiceCalendar`

**Aggregate Root:** `ServiceCalendar` — область действия: один календарный год.

**Сущности внутри агрегата:**
- `CalendarDay` — {дата, `DayType`}.

**Value Objects:**
- `DayType` (enum) — `Working | Weekend | Holiday | PreHoliday`.

**Инварианты:**
1. Каждая дата года представлена ровно одним `CalendarDay` (полное покрытие без пропусков и дублей).
2. `ServiceCalendar` года становится неизменяемым после публикации (`Published`) — используется расчётами как надёжная историческая основа; исправление ошибки после публикации создаёт новую версию календаря года с собственной историей, старые расчёты продолжают ссылаться на версию, действовавшую на момент расчёта.

## 5. Bounded Context: Scheduling *(Supporting Domain)*

### 5.1 Агрегат `DutySchedule` (График дежурств)

**Aggregate Root:** `DutySchedule` — область действия: один `UnitId` + один `AccountingPeriod`.

**Сущности внутри агрегата:**
- `PlannedShift` — {`EmployeeId`, `TimeInterval`, `DutyType`} — плановая смена/дежурство конкретного сотрудника.

**Value Objects:**
- `AccountingPeriod` — {`PeriodType`: Month|Quarter|Year, начало, конец}.
- `TimeInterval` — {начало, конец}; инвариант VO: начало строго раньше конца.
- `ScheduleStatus` (enum) — `Draft | Approved | Closed`.

**Инварианты:**
1. Внутри одного `DutySchedule` для одного `EmployeeId` не может быть двух `PlannedShift` с пересекающимися `TimeInterval` (физическая невозможность нести две смены одновременно).
2. Между окончанием одной `PlannedShift` и началом следующей `PlannedShift` того же сотрудника (в том числе через границу двух соседних `DutySchedule`, то есть двух периодов) должен соблюдаться минимальный межсменный отдых, значение которого не «зашито», а получено ссылкой на актуальную `RuleVersion` категории `MinimumRestPeriod`. Поскольку эта проверка может выходить за пределы одного агрегата (соседний период), она реализуется доменным сервисом (см. п. 8.1), а не инвариантом внутри одного агрегата.
3. `DutySchedule` в статусе `Approved` неизменяем: любое изменение состава смен после утверждения требует явной операции «пересмотр графика», порождающей новую версию с указанием причины и ссылкой на предыдущую.
4. `PlannedShift` не может быть назначена сотруднику, чей `EmploymentStatus` (в контексте Personnel, читается по ID) не равен `Active` на дату начала смены — сотрудник в отпуске/на больничном/отстранён не может быть планово назначен (кроме специально помеченного внепланового вызова, см. п. 6.1, инвариант 4).

---

## 6. Bounded Context: Time Accounting *(Core Domain)*

### 6.1 Агрегат `Timesheet` (Табель)

**Aggregate Root:** `Timesheet` — область действия: один `EmployeeId` + один `AccountingPeriod`. Это центральный агрегат всей модели.

**Сущности внутри агрегата:**
- `ServiceTimeEvent` — типизированная запись факта, абстрактный тип с вариантами:
  - `ActualShiftRecord` — {ссылка на `PlannedShift` (опционально, может отсутствовать при внеплановом вызове), фактический `TimeInterval`};
  - `SicknessRecord` — {`TimeInterval`};
  - `SuspensionRecord` — {`TimeInterval`, основание};
  - `OvertimeAttractionRecord` — {`TimeInterval`, обязательная ссылка на `OvertimeOrderId`};
  - `BusinessTripRecord` — {`TimeInterval`, место}.
- `CorrectionEntry` — запись, фиксирующая исправление ранее внесённого `ServiceTimeEvent`, всегда содержит причину и ссылку на исправляемую запись; сама по себе `CorrectionEntry` никогда не удаляет и не перезаписывает исходную запись (append-only история).

**Value Objects:**
- `HoursBreakdown` — **вычисляемый**, невладеющий (produced, not stored as source of truth) результат: {normHours, actualHours, nightHours, holidayHours, overtimeHours, underworkedHours} — производится применением `Rule`/`ConflictResolutionPolicy` к набору `ServiceTimeEvent` агрегата; не редактируется вручную.
- `TimesheetStatus` (enum) — `Open | PendingApproval | Approved | Reopened`.

**Инварианты:**
1. `ServiceTimeEvent` одного `Timesheet` не могут иметь пересекающихся `TimeInterval` — один и тот же момент времени не может быть одновременно, например, и болезнью, и фактической сменой (за исключением явно смоделированного случая «смена прервана болезнью», который выражается как **разбиение** на два непересекающихся события, а не наложение).
2. `OvertimeAttractionRecord` не может существовать без `OvertimeOrderId` — не бывает «сверхнормативного времени» без документа-основания (перенесено из бизнес-требования раздела 8 SRS в статус доменного инварианта — это правило целостности, а не просто рекомендация процесса).
3. Периоды `SicknessRecord` и `SuspensionRecord` исключаются из расчёта `underworkedHours` (недоработка не может вменяться по событиям, не зависящим от сотрудника) — это правило самого расчёта `HoursBreakdown`, но фиксируется как инвариант согласованности данных.
4. `Timesheet` в статусе `Approved` **неизменяем**: любое дальнейшее изменение возможно только через явный перевод в `Reopened` (с обязательным указанием ответственного и причины) с последующим повторным `Approved` — прямое редактирование запрещено на уровне модели, а не только процесса.
5. `HoursBreakdown` всегда пересчитывается детерминированно из (`ServiceTimeEvent`* + применимой на дату событий `RuleVersion` + `ConflictResolutionPolicy` + `ServiceCalendar`) — при повторном расчёте одних и тех же входных данных результат обязан быть идентичен (чистая функция без скрытого состояния); это прямо обеспечивает возможность «пересчитать переработку за любой год».
6. Сумма часов `ActualShiftRecord`, приходящихся на конкретный `EmployeeId` за сутки, не может физически превышать 24 часа (защита от ошибок ввода на уровне модели).

## 7. Bounded Context: Compensation *(Supporting Domain)*

### 7.1 Агрегат `CompensationCase` (Дело о компенсации)

**Aggregate Root:** `CompensationCase` — область действия: один `EmployeeId` + один `AccountingPeriod`, создаётся только после закрытия соответствующего `Timesheet`.

**Сущности внутри агрегата:**
- `CompensationLine` — {`RuleCategory` (Overtime/Night/Holiday), `HoursAmount`, `CompensationForm`, ссылка на обосновывающую `RuleVersion` (коэффициент/порядок)}.

**Value Objects:**
- `CompensationForm` (enum) — `Monetary | AdditionalRestTime`.
- `EmployeeElection` — {выбранная `CompensationForm`, дата волеизъявления} — опционален; отсутствие означает форму по умолчанию, определяемую `RuleVersion`.
- `CaseStatus` (enum) — `Draft | Finalized`.

**Инварианты:**
1. `CompensationCase` не может быть создан, пока `Timesheet` того же `EmployeeId`+`AccountingPeriod` не находится в статусе `Approved` (компенсация не может опережать факт).
2. Сумма `HoursAmount` по всем `CompensationLine` одной категории не может превышать соответствующее значение из `HoursBreakdown` утверждённого `Timesheet` — компенсация не может «придумывать» часы сверх зафиксированного факта.
3. `EmployeeElection` обязателен для тех `RuleCategory`, чья актуальная `RuleVersion` явно указывает `Scope` с допустимостью выбора сотрудником; для прочих категорий форма определяется правилом однозначно, и `EmployeeElection` не запрашивается (сама применимость выбора — атрибут правила, а не жёстко закодированное условие).
4. `CompensationCase` в статусе `Finalized` неизменяем; исправление возможно только новым `CompensationCase`-корректировкой, ссылающейся на предыдущее дело.

## 8. Bounded Context: Rest Balance *(Supporting Domain)*

### 8.1 Агрегат `RestDaysBalance` (Баланс дополнительных суток отдыха)

**Aggregate Root:** `RestDaysBalance` — область действия: один `EmployeeId`, ведётся на протяжении всей службы (не привязан к одному учётному периоду).

**Сущности внутри агрегата:**
- `BalanceMovement` — {тип: `Accrual | Consumption`, величина, дата, ссылка-основание: `CompensationLineId` для начисления или `RestUsageRequestId`/`LeaveGrantId` для списания}. Append-only, неизменяем после создания.

**Инварианты:**
1. В любой момент времени `сумма(Accrual) − сумма(Consumption) ≥ 0` — списание, превышающее остаток, невозможно (проверяется до создания движения `Consumption`, а не постфактум).
2. Каждый `Accrual` обязан ссылаться на существующий `CompensationLine` с `CompensationForm = AdditionalRestTime` — начисление ДДО не может возникнуть «из воздуха», вне процесса компенсации.
3. `BalanceMovement` не редактируется и не удаляется; ошибочное движение сторнируется симметричной обратной записью с указанием причины (append-only, полная трассируемость для служебной проверки).

## 9. Bounded Context: Leave Management *(Supporting Domain)*

### 9.1 Агрегат `LeaveGrant` (Отпуск)

**Aggregate Root:** `LeaveGrant` — область действия: одно предоставление отпуска одному `EmployeeId`.

**Сущности внутри агрегата:**
- `RecallEvent` — {дата отзыва, дата, с которой отпуск прерван} — при отзыве сотрудника из отпуска (ст. 65 ФЗ-141) фиксирует факт прерывания и делит период на «использованную» и «неиспользованную» части.

**Value Objects:**
- `LeaveType` (enum) — `Basic | Additional | PersonalCircumstances20YearsService | Maternity | ChildCare | Educational`.
- `LeavePeriod` — {начало, конец}.
- `EntitlementBasis` — ссылка на `RuleVersion` категории `LeaveEntitlement`, обосновывающая продолжительность (в т.ч. зависимость от `SeniorityDuration`).

**Инварианты:**
1. `LeavePeriod` одного `EmployeeId` не пересекается с `LeavePeriod` другого активного `LeaveGrant` того же сотрудника — за исключением специально смоделированного «присоединения» (Joining) двух смежных отпусков в единый непрерывный период, что не является пересечением, а стыковкой границ.
2. `LeaveType = PersonalCircumstances20YearsService` может быть выдан сотруднику **не более одного раза за весь период службы** — инвариант, требующий проверки по всей истории `LeaveGrant` сотрудника; поскольку это межагрегатная проверка (нужно видеть все прошлые `LeaveGrant`, а не только создаваемый), она обеспечивается доменным сервисом (см. 10.4), а не внутренним состоянием одного агрегата.
3. Наличие `RecallEvent` не уменьшает `EntitlementBasis` — неиспользованный остаток обязан быть учтён (запрещено «тихое» аннулирование дней отпуска); модель требует явного создания нового `LeaveGrant` или планового периода для неиспользованного остатка.
4. `LeaveGrant` не может быть создан с `LeavePeriod`, пересекающимся с уже утверждённой `PlannedShift` того же сотрудника в `Scheduling` без предварительной отмены/переноса этой смены (согласованность между контекстами обеспечивается доменным сервисом, а не прямой ссылкой между агрегатами разных контекстов).

## 10. Сквозные доменные сервисы (Domain Services)

Некоторые инварианты и вычисления по определению DDD не могут принадлежать одному агрегату, так как требуют одновременного взгляда на несколько агрегатов (иногда — из разных bounded context). Такая логика вынесена в доменные сервисы — они не хранят состояние, оперируют только доменными объектами.

### 10.1 `NormCalculationService`
Вычисляет `WeeklyNorm`/`PeriodNorm` для комбинации `Position` + `ServiceConditionCategory` + `AccountingPeriod`, используя актуальную на начало периода `RuleVersion` категории `NormCalculation` и `ServiceCalendar` соответствующего года. Чистая функция: одинаковые входные данные → одинаковый результат в любой момент времени (гарантия воспроизводимости исторических расчётов).

### 10.2 `HoursClassificationService`
Применяет `ConflictResolutionPolicy` к множеству `ServiceTimeEvent` одного `Timesheet`, производя непротиворечивый `HoursBreakdown` без задвоения часов между категориями (реализация инварианта 7.5 из SRS).

### 10.3 `RestPeriodPolicyService`
Проверяет соблюдение минимального межсменного отдыха между `PlannedShift`, потенциально принадлежащими двум разным (соседним по времени) агрегатам `DutySchedule`.

### 10.4 `LeaveEligibilityService`
Проверяет одноразовые/накопительные права на отпуск (например, `PersonalCircumstances20YearsService`), требующие анализа полной истории `LeaveGrant` сотрудника, а также согласованность запрашиваемого `LeavePeriod` с существующими `PlannedShift` в `Scheduling`.

### 10.5 `CompensationAllocationService`
На основании утверждённого `HoursBreakdown` и правил выбора формы компенсации формирует набор `CompensationLine` для `CompensationCase`, включая определение обязательности `EmployeeElection`.

## 11. Доменные события (Domain Events)

События фиксируют значимые с точки зрения бизнеса факты, произошедшие с агрегатами; они являются частью языка предметной области (и в дальнейшем могут использоваться для интеграции контекстов, но сами по себе — часть домена, а не техническая шина).

| Событие | Источник (агрегат) | Значение |
|---|---|---|
| `RuleVersionPublished` | `Rule` | Новая версия правила вступила в силу |
| `ScheduleApproved` | `DutySchedule` | График зафиксирован, дальнейшие изменения требуют пересмотра |
| `ShiftActuallyPerformed` | `Timesheet` | Смена подтверждена фактом |
| `SicknessRegistered` | `Timesheet` | Зарегистрирован факт временной нетрудоспособности |
| `OvertimeAttracted` | `Timesheet` | Зафиксировано привлечение сверх нормы на основании приказа |
| `TimesheetApproved` | `Timesheet` | Период закрыт, `HoursBreakdown` зафиксирован окончательно |

| `CompensationCaseFinalized` | `CompensationCase` | Компенсация по периоду определена окончательно |

| `RestDaysConsumed` | `RestDaysBalance` | Списаны дополнительные сутки отдыха |

## 13. Итог

Модель построена так, что **источником истины о величине норм, коэффициентов и правил классификации времени всегда является `Rule`/`RuleVersion`**, а не атрибуты сотрудника, должности или табеля. Все расчётные агрегаты (`Timesheet`, `CompensationCase`, `LeaveGrant`, `DutySchedule`) ссылаются на конкретную версию правила, действовавшую **на дату события**, что структурно гарантирует требование — пересчитать переработку, компенсацию или норму за любой прошлый год, воспроизводимо и без искажения истории.

Ключевые тактические принципы DDD, применённые последовательно:
- Каждый агрегат — собственная граница согласованности (consistency boundary): инварианты внутри агрегата обеспечиваются им самим; инварианты, требующие данных из нескольких агрегатов, вынесены в доменные сервисы, а не «размазаны» по агрегатам.
- Ссылки между агрегатами — только по идентификатору, никогда не по прямой ссылке на объект (в т.ч. между bounded contexts).
- История никогда не перезаписывается — исправления везде выражены как новые версии/события (`RuleVersion`, `CorrectionEntry`, `RecallEvent`, `TimesheetReopened`), что одновременно удовлетворяет требованию аудируемости и требованию точного восстановления расчётов задним числом.
