# Архитектура приложения (v2, пересобрано с нуля)
## Система расчёта служебного времени сотрудников ФПС России

**Кода нет.** Документ описывает исключительно структуру: архитектурные решения, слои, модули, папки, границы, зависимости, диаграммы — построено на основании ранее спроектированной Domain Model.

## 1. Архитектурные драйверы (откуда берутся требования к структуре)

Прежде чем выбирать структуру, зафиксируем, что именно домен и нефункциональные требования *вынуждают* архитектуру делать:

| № | Драйвер | Источник | Следствие для архитектуры |
|---|---|---|---|
| Д1 | Правило — первичный объект, а не сотрудник (`Rule → Calculation → Employee`) | Domain Model, п.0 | `Legal Rules & Calculation` — отдельный модуль-ядро, от которого зависят остальные, а не наоборот |
| Д2 | Инварианты живут внутри границ конкретных агрегатов (`Timesheet`, `Rule`, `LeaveGrant`...) | Domain Model, разд. 2–9 | Каждый bounded context = изолированный модуль с собственным Domain-слоем; между модулями — только ссылки по идентификатору |
| Д3 | История никогда не перезаписывается (`RuleVersion`, `CorrectionEntry`, append-only) | Domain Model, разд. 13 | Хранилище и API записи проектируются как «добавление факта», а не «обновление записи» — влияет на конструкцию репозиториев (не на данный документ напрямую, но ограничивает инфраструктуру) |
| Д4 | 1 000 000+ пользователей, преимущественно **читающих** свой табель/баланс | Постановка задачи | Резкая асимметрия чтение/запись → кандидат на CQRS именно там, где эта асимметрия есть |
| Д5 | Запрет микросервисов | Постановка задачи | Один деплой-артефакт; изоляция — только на уровне кода/модулей, не сети |
| Д6 | Компенсация не может начисляться без документа-основания; переработка не может быть учтена без приказа | SRS, разд. 8 п.11; Domain Model, инвариант 6.1.2 | Межмодульная связь `TimeAccounting → Compensation → RestBalance` обязана быть прослеживаемой цепочкой событий, а не независимыми действиями |

Все решения ниже — это ответы на Д1–Д6, а не произвольный выбор шаблонов.

## 2. Выбор архитектурного стиля (ADR)

**Решение:** Модульный монолит (**Modular Monolith**).

**Обоснование через принцип исключения:**
- Микросервисы дают изоляцию ценой распределённых транзакций и сетевых отказов — не нужны, так как Д5 их прямо исключает, а Д2 (изоляция агрегатов) достижима на уровне кода.
- Классический слоистый монолит («один Application-слой на всё приложение») плохо масштабируется по сложности — Д1/Д2 требуют явных границ по bounded context, иначе логика Rule/Timesheet/Compensation расползается.
- **Модульный монолит** даёт границы Д2 без стоимости Д5-запрещённого стиля, и остаётся единым артефактом для простоты эксплуатации.

**Внутри каждого модуля** используется Clean Architecture (порядок зависимостей) + DDD (что лежит в Domain-слое) + Vertical Slice Architecture (как организован Application-слой). **CQRS** применяется выборочно, только к модулям, где подтверждён Д4.

## 3. Слоистая модель внутри модуля (Clean Architecture)

```
                    ЗАВИСИМОСТИ ТОЛЬКО ВНУТРЬ →

  ╔══════════════════════════════════════════════════════════════╗
  ║  PRESENTATION                                                    ║
  ║  (входная точка: HTTP-контроллер / обработчик очереди)            ║
  ║  ┌──────────────────────────────────────────────────────────┐  ║
  ║  │  INFRASTRUCTURE                                             │  ║
  ║  │  (реализация портов: репозитории, кэш, шина событий)         │  ║
  ║  │  ┌────────────────────────────────────────────────────┐  │  ║
  ║  │  │  APPLICATION                                          │  │  ║
  ║  │  │  (Vertical Slices: Command/Query + Handler)            │  │  ║
  ║  │  │  здесь же объявлены порты (интерфейсы репозиториев)     │  │  ║
  ║  │  │  ┌──────────────────────────────────────────────┐  │  │  ║
  ║  │  │  │  DOMAIN                                        │  │  │  ║
  ║  │  │  │  Aggregates / Entities / Value Objects /        │  │  │  ║
  ║  │  │  │  Domain Events / Domain Services                │  │  │  ║
  ║  │  │  │  НОЛЬ зависимостей наружу                        │  │  │  ║
  ║  │  │  └──────────────────────────────────────────────┘  │  │  ║
  ║  │  └────────────────────────────────────────────────────┘  │  ║
  ║  └──────────────────────────────────────────────────────────┘  ║
  ╚══════════════════════════════════════════════════════════════╝
```

**Правило (Dependency Rule), проверяемое статически:**
- `Domain` не импортирует ничего из `Application`, `Infrastructure`, `Presentation`.
- `Application` импортирует только `Domain` (своего модуля) и `BuildingBlocks`.
- `Infrastructure` реализует интерфейсы, объявленные в `Application`/`Domain` (инверсия зависимостей — сама `Infrastructure` не диктует форму этих интерфейсов).
- `Presentation` знает только об `Application` (через диспетчер команд/запросов), никогда — о `Domain` напрямую.

```
└────────────────────────┘        └────────────────────┘

Правило: любая стрелка = зависимость от Contracts модуля-источника,
НИКОГДА от его Domain или Infrastructure.
```

### 4.2 Правила границ (жёсткие)
1. Модуль может импортировать только папку `Contracts/` другого модуля.
2. `Contracts/` содержит исключительно: (а) интерфейсы запросов на чтение публичных фактов (например, «действует ли эта версия правила на дату Х», «утверждён ли табель»), (б) описания интеграционных событий.
3. Ни один Query-контракт не возвращает сам объект чужого агрегата — только проекцию/DTO, принадлежащую вызывающей стороне по смыслу (Anti-Corruption Layer на границе).
4. `LegalRulesAndCalculation` не имеет входящих зависимостей содержательного типа — только он публикует Open Host Service, сам не потребляет ничьи контракты (согласуется с Д1).

## 6. Анатомия вертикального среза (одинаковая форма во всех модулях)

```
<UseCaseName>/
 ├─ <UseCaseName>Command | Query      — value object запроса, неизменяемый
 ├─ <UseCaseName>Validator            — проверка ФОРМЫ запроса (не бизнес-инвариантов)
 └─ <UseCaseName>Handler              — оркестрация: порт репозитория → метод агрегата
                                        (для Command) или чтение read-модели (для Query)
```

**Важно:** бизнес-инварианты не проверяются в `Handler` — они уже инкапсулированы в методах агрегата (`Timesheet.RegisterActualShift()`, `Rule.PublishVersion()` и т.д., см. Domain Model). Обработчик — координатор, а не место принятия решений.

Три показательных среза:

| Слайс | Модуль | Тип | Что делает |
|---|---|---|---|
| `RegisterActualShift` | TimeAccounting | Command | Загружает `Timesheet` через Write-порт → вызывает доменный метод → сохраняет → пишет событие в Outbox |
| `GetMyTimesheetSummary` | TimeAccounting | Query | Читает готовую денормализованную проекцию `HoursBreakdown`, агрегат не трогается |
| `RegisterEmployee` | PersonnelAndOrganization | Command (без CQRS) | Загружает/создаёт `Employee` через единственный репозиторий; тот же репозиторий обслуживает и чтение — отдельная read-модель не нужна |

## 8. CQRS — решение по каждому модулю отдельно

### 8.1 Критерий применения (нужно хотя бы одно условие)
1. Соотношение чтение/запись экстремально асимметрично (Д4).
2. Модель, удобная для соблюдения инвариантов при записи, непригодна для агрегаций/срезов при чтении.
3. Число читающих на порядки больше числа пишущих (1 000 000 сотрудников-читателей vs. ограниченный штат табельщиков-писателей).

### 8.2 Результат применения критерия

| Модуль | CQRS? | Обоснование |
|---|---|---|
| `TimeAccounting` | **Да** | Максимальная асимметрия в системе: каждый из 1 000 000+ сотрудников многократно смотрит свой табель/баланс, при этом операций записи на порядки меньше |
| `Compensation` | **Частично** (только Query-сторона отчётности) | Командная часть (`CreateCompensationCase`, `FinalizeCase`) — обычная работа с агрегатом; аналитика/прогноз по региону требует агрегаций, не связанных с формой агрегата |
| `LegalRulesAndCalculation` | Нет | Записи крайне редки (публикация версии правила — административное событие); чтение — точечный lookup по ключу, решается кэшем без отдельной read-модели |
| `PersonnelAndOrganization` | Нет | Классический справочный CRUD без асимметрии, оправдывающей раздельные модели |
| `ServiceCalendar` | Нет | Статичные данные года, кэшируются целиком |
| `Scheduling` | Нет | Чтение графика по сложности сопоставимо с записью |
| `RestBalance`, `LeaveManagement` | Нет | Умеренная частота чтения, агрегат достаточно прост для прямого чтения |

Введение CQRS в правой части таблицы добавило бы стоимость синхронизации без измеримой выгоды — что противоречит требованию «только там, где действительно необходимо».

## 9. Межмодульная коммуникация: два механизма

### 9.1 Синхронный вызов через публичный контракт (нужна сильная согласованность)
Пример: `Compensation` не может создать `CompensationCase`, пока не убедится, что `Timesheet` утверждён (жёсткий инвариант). Он вызывает Query-контракт модуля `TimeAccounting` — в рамках одного процесса, без сети:

```
Compensation.Application.CreateCompensationCaseHandler
        │  вызывает порт
        ▼
TimeAccounting.Contracts.IGetTimesheetStatus
        │  реализация обращается к внутреннему Query-обработчику
        ▼
TimeAccounting.Application.Queries.GetTimesheetStatus
```

### 9.2 Асинхронный обмен через доменные/интеграционные события (допустима конечная согласованность)
Механизм — **Transactional Outbox**: изменение состояния агрегата и запись исходящего события происходят в одной локальной транзакции; отдельный воркер публикует событие позже.

```
Timesheet.Approve()
   │ (одна транзакция)
   ├─ изменение состояния Timesheet
   └─ запись в Outbox: TimesheetApproved
            │  (асинхронно, воркер Composition/Workers)
            ▼
     публикация TimesheetApproved
            ├──▶ Compensation.Application  (создать CompensationCase)
            └──▶ TimeAccounting.Infrastructure.Read  (перестроить read-проекцию)

CompensationCase.Finalize()
   │
   └─ запись в Outbox: CompensationLineCreated
            ▼
     RestBalance.Application  (начислить Accrual — ТОЛЬКО в ответ на событие,
                                прямой внешний вызов начисления запрещён — Д6)
```

Это единственный способ, которым в модели физически может появиться начисление ДДО — что и требовалось инвариантом Domain Model (8.1.2): «нет начисления без основания».

## 10. Presentation / Composition Root

- `Composition/Api` — входная точка HTTP (или иного канала), не содержит бизнес-логики, только отображение внешнего запроса на `Command`/`Query` конкретного модуля.
- `Composition/Workers` — та же кодовая база, другая точка входа: обработка outbox, построение read-проекций, плановые фоновые пересчёты.
- `Composition/ModuleRegistration` — единственное место, регистрирующее зависимости всех модулей; сами модули друг о друге не знают.
- Сквозные задачи (авторизация по ролям из SRS, логирование, трассировка, валидация формы запроса) реализованы как единый конвейер в `BuildingBlocks/Application`, применяемый одинаково ко всем слайсам — не дублируется в каждом обработчике.

## 11. Инфраструктурный слой — назначение портов (без диктата технологий)

| Порт (объявлен в Application/Domain) | Роль |
|---|---|
| Репозиторий агрегата (Write) | Загрузка/сохранение одного агрегата целиком, атомарно с записью в Outbox |
| Read-модель (только у CQRS-модулей) | Денормализованная проекция, обновляемая асинхронно из событий, не проходит через агрегат |
| Кэш справочных данных | Для `Rule`/`ServiceCalendar` — инвалидация по событию публикации новой версии |
| Transactional Outbox | Таблица/структура в той же единице транзакции, что и агрегат |
| Шина интеграционных событий | Абстракция `IEventBus`, скрывает конкретного брокера |

Технологический выбор реализации этих портов — предмет отдельного документа (Infrastructure Design), не архитектуры домена.

```
              ┌───────────────────────┼───────────────────────┐
              ▼                       ▼                       ▼
      ┌───────────────┐       ┌───────────────┐       ┌───────────────┐
      │ Инстанс Api #1  │  ...  │ Инстанс Api #N  │       │  (та же сборка,│
      │ (stateless)      │       │ (stateless)      │       │   роль: Api)    │
      └───────┬───────┘       └───────┬───────┘       └───────────────┘
       Command-путь │                   │ Query-путь
              ▼                        ▼
   ┌─────────────────────┐   ┌─────────────────────────┐
   │ Первичная БД (write)  │──▶│ Реплики для чтения /       │
   │  консистентная запись  │   │ read-проекции (CQRS) + кэш │
   └───────────┬───────────┘   └─────────────────────────┘
               │ outbox
               ▼
   ┌─────────────────────┐
   │ Брокер событий          │
   └───────────┬───────────┘
               ▼
   ┌─────────────────────┐
   │ Инстансы Workers        │  (та же сборка, роль: Workers,
   │ (горизонтально            │   масштабируются независимо от Api)
   │  масштабируемы)           │
   └─────────────────────┘
```

### 12.2 Факторы, обеспечивающие масштаб (каждый — прямое следствие драйверов Д1–Д6)

| Фактор | Как связан с драйверами |
|---|---|
| Stateless API-слой, горизонтально масштабируемый | Базовое условие для линейного роста числа читающих сотрудников (Д4) |
| Разделение чтения/записи (CQRS в `TimeAccounting`/`Compensation`) | Прямой ответ на Д4 — самая частая операция (просмотр баланса) не конкурирует с редкой операцией записи за одни и те же ресурсы |
| Кэш справочных данных (`Rule`, `ServiceCalendar`) | Эти данные читаются на каждый расчёт, но меняются редко (Д1) — агрессивное кэширование снимает основную часть нагрузки на БД |
| Асинхронная обработка через Outbox + Workers | Позволяет держать write-путь быстрым и при этом гарантированно (Д6) выполнять цепочку начислений без блокировки ответа пользователю |
| Партиционирование данных по `UnitId`/региону (опционально, при росте) | Домен иерархичен по организационной структуре — естественный ключ шардирования без изменения модульных границ |
| Изоляция модулей (границы разд. 4.2) | Позволяет масштабировать/оптимизировать только «горячий» модуль (`TimeAccounting`), не трогая остальные семь |

### 12.3 Почему это не требует микросервисов
Всё перечисленное — свойства **данных и процесса развёртывания**, а не сетевой границы. Строгие модульные границы дают изоляцию, обычно приписываемую микросервисам, без цены распределённых транзакций и независимого версионирования контрактов между отдельно деплоящимися сервисами (Д5).

## 13. Сквозной пример (двумя потоками)

### 13.1 Запись
```
HTTP → Composition/Api → RegisterActualShiftCommand
     → pipeline (авторизация роли, валидация формы)
     → TimeAccounting.Application.Commands.RegisterActualShift.Handler
        → Timesheet (Write-репозиторий) → доменный метод проверяет инварианты
        → сохранение агрегата + запись Outbox (одна транзакция)
     ← ответ клиенту сразу, без ожидания асинхронных последствий

(позже, асинхронно)
Worker → читает Outbox → публикует ShiftActuallyPerformed
     → TimeAccounting.Infrastructure.Read перестраивает проекцию HoursBreakdown
```

### 13.2 Чтение
```
HTTP → Composition/Api → GetMyTimesheetSummaryQuery
     → pipeline (сотрудник видит только свои данные)
     → TimeAccounting.Application.Queries.GetMyTimesheetSummary.Handler
        → читает ГОТОВУЮ read-проекцию (агрегат не загружается, не пересчитывается)
     ← ответ клиенту с низкой задержкой независимо от нагрузки на запись
```

## 14. Тестируемость, вытекающая из границ

| Слой | Способ тестирования |
|---|---|
| Domain | Модульные тесты агрегатов/инвариантов — чистые объекты, без фейков |
| Application (слайс) | Тест обработчика с фейковым портом репозитория — проверяется оркестрация |
| Infrastructure | Интеграционные тесты реализации портов против реальной инфраструктуры |
| Межмодульные контракты | Контрактные тесты потребителя против опубликованного `Contracts/`, без обращения к внутренностям модуля-поставщика |
