# Внутренний контроль соответствия обработки персональных данных

Утверждён оператором {{ФИО_ОПЕРАТОРА}} «{{ДАТА_ВСТУПЛЕНИЯ}}».

Основания: п. 4 ч. 1 ст. 18.1 Федерального закона от 27.07.2006 № 152-ФЗ
(осуществление внутреннего контроля соответствия обработки персональных
данных закону и принятым в соответствии с ним актам) и п. 9 ч. 2 ст. 19
(контроль за принимаемыми мерами и уровнем защищённости).

**Главная мысль документа.** Контроль, который выполняет человек по памяти,
не выполняется. Поэтому большая часть проверок здесь — машинные: они идут
при каждом изменении кода и каждую ночь, а их отказ приходит письмом.
Человеку остаётся то, что машине не поручить: сверить документы с
действительностью и посмотреть на журнал своими глазами.

## 1. Что проверяется машиной

| Когда | Что проверяется | Чем |
|---|---|---|
| При каждом изменении кода | версии и хэши документов совпадают в трёх местах; в опубликованных текстах нет незаполненных подстановок | `node scripts/legal.mjs` в CI |
| То же | в технические журналы не попадают адреса почты, ключи, блоба; журнал остаётся машиночитаемым | тесты `api/tests/test_logging.py` |
| То же | состав боевой установки не открывает лишнего: у базы нет порта наружу, у приложения только петля, журналы ограничены, права отобраны | тесты `api/tests/test_deploy.py`, проверка состава в CI |
| То же | сроки хранения исполняются кодом, а не только обещаны | тесты `api/tests/test_retention.py` |
| То же | миграции применяются и откатываются, схема не разошлась с моделями | джоба «API» |
| Ежесуточно, 03:17 | исполнение сроков: надгробия, ревизии, журнал событий, протухшие токены, брошенные регистрации | `grafik-gc.timer` → `python -m grafik_api.cli gc` |
| Ежесуточно, 02:40 | резервная копия создана и зашифрована | `grafik-backup.timer` |
| Ежесуточно, 03:40 | копия свежая, не пустая, зашифрована; незашифрованных выгрузок в каталоге нет | `grafik-backup-verify.timer` |
| При отказе любой из задач | письмо оператору | `grafik-notify-failure@.service` |

Отказ машинной проверки — это и есть событие внутреннего контроля: он
попадает в журнал (раздел 5) с отметкой, что сделано.

## 2. Что проверяет оператор

### Раз в два рабочих дня

* **Почта `grafik1-3@yandex.ru`.** Срок ответа субъекту считается со дня
  обращения, а не со дня прочтения (ч. 1 ст. 20 152-ФЗ), поэтому ящик
  нельзя оставлять без присмотра дольше.

### Ежемесячно

* **Проверка разворачивания резервной копии** на своей машине —
  `deploy/restore-check.sh`. Автоматическая проверка на сервере отвечает
  только на вопрос «копия есть и зашифрована»: закрытого ключа там нет.
* **Обновления безопасности** операционной системы сервера и образов
  (`apt upgrade`, пересборка образа приложения при обновлении базового).
* **Просмотр журнала событий безопасности** на предмет необычного: всплески
  отказов входа, срабатывания защиты от перебора, повторные использования
  refresh-токенов.

```bash
docker compose -f /opt/grafik13/compose.prod.yml exec -T postgres \
  psql -U grafik -d grafik -c "
    SELECT date_trunc('day', at) AS сутки, event, count(*)
    FROM audit_log
    WHERE at > now() - interval '30 days'
      AND event LIKE '%failed%' OR event LIKE '%rate%'
    GROUP BY 1, 2 ORDER BY 1 DESC, 3 DESC LIMIT 40"
```

### Ежеквартально

* **Фактическая проверка сроков хранения.** Проверка не того, что задача
  запускалась, а того, что в базе действительно не осталось просроченного.
  Все числа должны быть нулями (запрос проверен):

```bash
docker compose -f /opt/grafik13/compose.prod.yml exec -T postgres \
  psql -U grafik -d grafik -v ON_ERROR_STOP=1 -c "
SELECT 'надгробия старше 180 дней' AS что, count(*) AS сколько FROM blobs
  WHERE deleted_at IS NOT NULL AND deleted_at < now() - interval '180 days'
UNION ALL SELECT 'ревизии старше 30 дней', count(*) FROM blob_revisions
  WHERE written_at < now() - interval '30 days'
UNION ALL SELECT 'журнал старше 180 дней', count(*) FROM audit_log
  WHERE at < now() - interval '180 days'
UNION ALL SELECT 'протухшие сессии', count(*) FROM refresh_tokens
  WHERE expires_at < now()
UNION ALL SELECT 'протухшие ссылки', count(*) FROM one_time_tokens
  WHERE expires_at < now()
UNION ALL SELECT 'брошенные регистрации старше 30 дней', count(*) FROM users u
  WHERE u.email_verified_at IS NULL AND u.created_at < now() - interval '30 days'
    AND NOT EXISTS (SELECT 1 FROM blobs b WHERE b.user_id = u.id)
UNION ALL SELECT 'аккаунтов всего (предел уровня защищённости — 100 000)',
  count(*) FROM users"
```

* **Сверка карты данных с кодом.** Правило «нет строки в карте — нет данных
  в коде» проверяется в обе стороны: по миграциям за квартал — не появилось
  ли колонки, которой нет в карте; по карте — не исчезло ли что-то из кода.
* **Открытые порты и правила экрана:** `ss -ltnp` и `nft list table inet
  grafik` — снаружи доступны 22, 80, 443 и ничего больше.
* **Срок сертификата** и работа его обновления (`certbot renew --dry-run`).
* **Перечень лиц, допущенных к персональным данным** — не появилось ли
  фактического доступа у кого-то ещё (подрядчик, помощник).
* **Статус нового приказа ФСТЭК России взамен приказа № 21** — см.
  [`04-perechen-mer.md`](04-perechen-mer.md), раздел 6. Вступил в силу —
  перечень мер переделывается, и проводится оценка «уровня зрелости».

### Ежегодно

* **Пересмотр документов:** положение, акт об уровне защищённости, модель
  угроз, оценка вреда, перечень мер, этот документ. У каждого — отметка в
  «Истории редакций», даже если текст не изменился (запись «пересмотрено,
  изменений нет» — тоже результат).
* **Проверка числа субъектов:** приближение к 100 000 меняет уровень
  защищённости (акт, раздел 3).
* **Проверка актуальности сведений в уведомлении Роскомнадзора**: при
  изменении сведений оператор обязан уведомить об изменении (ч. 7 ст. 22
  152-ФЗ).
* **Сверка редакций норм**, на которые ссылаются документы: таблица в
  [`README.md`](README.md).

## 3. Что проверяется при каждом изменении обработки

Не по расписанию, а по событию — любое из перечисленного требует проверки
до выкладки:

* появилась новая колонка в базе или новое поле в блобе → карта данных,
  политика, при необходимости согласие;
* появилась новая ручка API, отдающая персональные данные → карта данных,
  модель угроз;
* появился новый обработчик (внешний отправщик писем, сторонний сервис) →
  карта данных, политика, договор поручения, уведомление в Роскомнадзор;
* изменился срок хранения → контракт, карта данных, политика, код
  (`services/retention.py`, `services/sync.py`) и тесты сроков.

## 4. Оценка эффективности мер до ввода в эксплуатацию

Пункт 4 ч. 2 ст. 19 152-ФЗ требует оценить эффективность принимаемых мер
**до ввода информационной системы в эксплуатацию**. Для этой системы
«ввод в эксплуатацию» — день, когда на сайте включается регистрация.

До этого дня проверяется и записывается в журнал:

| Что | Как проверяется |
|---|---|
| Сквозной сценарий работает | регистрация → правка на устройстве А → синхронизация → появление на устройстве Б → расхождение → смена пароля → выгрузка → удаление аккаунта |
| Содержимое на сервере нечитаемо | взять блоб из базы напрямую и убедиться, что он не разбирается без ключа |
| Сроки исполняются | запрос из раздела 2 на «ежеквартально» даёт нули; `cli gc` отработал |
| Копия разворачивается | `deploy/restore-check.sh` на чистой машине, с проверкой таблиц и числа строк |
| В журналах нет персональных данных | поиск по журналу: ни одного адреса почты, ни одного блоба |
| Документы опубликованы и совпадают с кодом | `/privacy`, `/consent`, `/terms` открываются; `GET /legal/documents` отдаёт те же версии и хэши |
| Уведомление подано | Роскомнадзор — до начала обработки (ст. 22) |
| Защитные заголовки и TLS на месте | проверка ответов сервера |
| Межсетевой экран и `fail2ban` работают | `nft list table inet grafik`, `fail2ban-client status sshd` |

Это же — чек-лист приёмки: он сверяется с шагом 16 плана, чтобы приёмка и
оценка эффективности были одной работой, а не двумя.

## 5. Журнал внутреннего контроля

Хранится у оператора (в репозитории — только форма: записи могут содержать
сведения о неполадках, которые не стоит публиковать).

| № | Дата | Вид проверки | Что проверялось | Результат | Что сделано | Срок устранения |
|---|---|---|---|---|---|---|
| 1 | | плановая (месяц/квартал/год) / по событию / отказ машинной проверки / после инцидента | | соответствует / выявлено | | |

Правила:

* запись делается в день проверки, а не в конце квартала;
* выявленное несоответствие закрывается записью «что сделано», а не
  забывается;
* записи по итогам инцидента ссылаются на материалы расследования
  ([`07-reglament-incidenta.md`](07-reglament-incidenta.md));
* журнал предъявляется Роскомнадзору при проверке — он и есть доказательство
  того, что внутренний контроль не фикция.

## 6. Известные расхождения, которые надо закрыть

Внутренний контроль начинается с того, что известно уже сейчас:

| Что | Почему это расхождение | Что сделать |
|---|---|---|
| Сборка мусора пишет только в технический журнал приложения (`sync.gc`, `retention.collect`), а не в журнал событий безопасности | приказ Роскомнадзора № 179 ждёт выгрузку из журнала регистрации событий информационной системы; для уничтожения по сроку такой выгрузкой служит запись технического журнала, а он живёт меньше | решить, заводить ли событие в `audit_log` на уничтожение по сроку; вопрос к пересмотру модели и кода |
| Приказ № 179 предполагает в акте фамилию, имя и отчество субъекта | оператор ими не располагает и не собирает | позиция изложена в [`06-poryadok-unichtozheniya.md`](06-poryadok-unichtozheniya.md), раздел 4.2; вопрос к юристу |
| Порядок информирования ГосСОПКА (приказ ФСБ России № 77) не сверен по действующей редакции | в ноябре 2025 года группа приказов обновлялась | сверить до начала обработки; [`07-reglament-incidenta.md`](07-reglament-incidenta.md), раздел 5 |
| Тексты ряда норм приведены по открытым публикациям | официальные источники из окружения разработки недоступны | сверить в справочной правовой системе перед подписанием; таблица в [`README.md`](README.md) |
