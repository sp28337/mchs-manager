# Боевое развёртывание сервера синхронизации

Этот каталог — всё, что нужно, чтобы поднять сервер «График 1 3» и
обслуживать его. Про выкладку **сайта** (статика, nginx, посещаемость) —
`DEPLOYMENT.md` в корне; здесь про **API**, базу, резервные копии и
расписания.

Файлы:

| Файл | Что это |
|---|---|
| `compose.prod.yml` | боевой состав: база и API (+ одноразовые `migrate` и `gc`) |
| `env.prod.example` | образец `api.env` — какие переменные читает приложение |
| `nginx-site.conf` | настройка сайта; в ней же `location ^~ /api/` для API |
| `nginx-security-headers.conf` | защитные заголовки, подключаются в каждый `location` |
| `nginx-metrics.conf`, `site-metrics`, `site-metrics.logrotate` | посещаемость сайта без персональных данных |
| `nftables.conf` | межсетевой экран |
| `fail2ban-jail.local` | загон для ssh (и объяснение, почему для API его нет) |
| `backup.sh` | резервная копия базы: выгрузка и шифрование открытым ключом |
| `backup-verify.sh` | ежедневная проверка копий — та, что возможна без закрытого ключа |
| `restore-check.sh` | разворачивание копии: проверяется руками и не на сервере |
| `notify-failure.sh` | письмо владельцу, когда задача по расписанию упала |
| `systemd/` | службы и таймеры: сборка мусора, копии, проверка копий |

## Как это устроено на сервере

```
                интернет
                   │  443/tcp
        ┌──────────┴───────────┐
        │   nginx (хозяин)     │  TLS, сертификат certbot
        │                      │
        │  /            статика сайта из /var/www/grafik13/current
        │  /api/        прокси на 127.0.0.1:8001
        └──────────┬───────────┘
                   │
        ┌──────────┴──────────────────────────────┐
        │  docker, сеть 172.28.0.0/24             │
        │                                         │
        │   api (gunicorn + uvicorn)  :8000       │
        │     └── публикуется как 127.0.0.1:8001  │
        │   postgres                 :5432        │ порта наружу нет
        └─────────────────────────────────────────┘
                   │ 25/tcp на шлюз 172.28.0.1
        ┌──────────┴───────────┐
        │  postfix (хозяин)    │  письма о подтверждении адреса
        └──────────────────────┘
```

Три решения, которые стоит понять до установки.

**nginx один и на хозяине машины.** В составе его нет: он уже стоит, отдаёт
сайт и держит сертификат certbot. Второй nginx в контейнере спорил бы за
443-й порт и потребовал бы второго сертификата на то же имя. Поэтому API
живёт за тем же nginx — одно имя, один сертификат, одни защитные
заголовки.

**API слушает только петлю.** В составе порт публикуется как
`127.0.0.1:8001`, то есть снаружи к приложению не подойти ничем, кроме
nginx. У базы порта нет вовсе: с ней говорит только API по внутренней сети.

**Подсеть задана явно (172.28.0.0/24).** Приложению нужно знать адрес, с
которого приходит nginx, — это шлюз моста `172.28.0.1`, — чтобы доверять
его заголовку `X-Forwarded-For`. Иначе в журнал событий и в счётчик попыток
входа попадал бы один и тот же адрес шлюза, то есть защита от перебора
считала бы попытки всех людей в одну кучу. Этот адрес упомянут в трёх
местах: `compose.prod.yml` (сеть), `api.env` (`GRAFIK_TRUSTED_PROXIES`),
`nftables.conf` (почта из контейнера). Меняется во всех трёх сразу.

## Установка с нуля

Делается один раз. Дальше выкладка автоматическая
(`.github/workflows/api-cd.yml`).

### 1. Пакеты

```bash
sudo apt update
sudo apt install -y docker.io docker-compose-v2 age nftables fail2ban postfix rsync curl
```

`postfix` при установке спросит тип — «Internet Site», имя системы
`grafik13.ru`.

### 2. Каталоги

```bash
sudo install -d -m 755 /opt/grafik13          # состав, скрипты
sudo install -d -m 700 /etc/grafik13          # получатели копий, адрес для писем о сбоях
sudo install -d -m 700 /var/backups/grafik13  # сами копии
```

### 3. Ключ для резервных копий — НА СВОЕЙ МАШИНЕ, не на сервере

```bash
age-keygen -o ~/.config/grafik13/backup-key.txt
chmod 600 ~/.config/grafik13/backup-key.txt
# в выводе строка «# public key: age1...» — она и нужна серверу
```

Закрытый ключ остаётся у владельца: на своей машине и копией в надёжном
месте (бумага в сейфе, второй носитель). На сервере — только открытый:

```bash
echo 'age1...' | sudo tee /etc/grafik13/backup-recipients.txt
sudo chmod 600 /etc/grafik13/backup-recipients.txt
```

Смысл в том, что взломавший сервер получит доступ к живой базе — с этим
ничего не сделать, — но не к архиву за месяц. Обратная сторона честная:
**потерял закрытый ключ — потерял все копии.** Поэтому ключ копируется
раньше, чем появляется первая копия, а разворачивание проверяется раз в
месяц (ниже).

### 4. Секреты приложения

```bash
sudo cp /opt/grafik13/env.prod.example /opt/grafik13/api.env   # или из репозитория
sudo chmod 600 /opt/grafik13/api.env
sudo nano /opt/grafik13/api.env
```

Заполнить:

```bash
openssl rand -base64 48   # → GRAFIK_PEPPER
openssl rand -base64 48   # → GRAFIK_JWT_SECRET
openssl rand -base64 36   # → пароль базы, он же в двух местах
```

Пароль базы пишется и в `api.env` (внутри `GRAFIK_DATABASE_URL`), и в
отдельный файл для самой базы:

```bash
printf 'POSTGRES_PASSWORD=%s\n' 'ТОТ_ЖЕ_ПАРОЛЬ' | sudo tee /opt/grafik13/postgres.env
sudo chmod 600 /opt/grafik13/postgres.env
```

**`GRAFIK_PEPPER` — особый секрет.** Он участвует в хэше проверочного
значения пароля, и его смена равна «не войдёт никто и никогда»:
восстановить по ключу восстановления тоже не получится. Хранить его надо
так же бережно, как закрытый ключ копий, и вместе с ними — потому что
копия базы без перца бесполезна.

Адрес для писем о сбоях:

```bash
printf 'ALERT_TO=вы@example.org\n' | sudo tee /etc/grafik13/alerts.env
sudo chmod 600 /etc/grafik13/alerts.env
```

### 5. Почта из контейнера

Приложение отправляет письма о подтверждении адреса и восстановлении
доступа через свой postfix на хозяине машины — внешний отправщик стал бы
вторым обработчиком персональных данных (раздел 4
`docs/legal/data-map.md`), а это договор поручения и строка в уведомлении
Роскомнадзора.

В `/etc/postfix/main.cf`:

```
inet_interfaces = all
mynetworks = 127.0.0.0/8 [::1]/128 172.28.0.0/24
```

`inet_interfaces = all`, а не адрес шлюза: интерфейс моста создаёт docker,
и при загрузке машины его может ещё не быть — postfix тогда не поднимется
вовсе. Доступ снаружи закрывает межсетевой экран: 25-й порт открыт только
подсети контейнеров (`nftables.conf`).

Чтобы письма доходили, а не падали в спам, нужны три записи вне сервера —
их заводит владелец домена:

* **PTR** (обратная запись) у провайдера VPS — на `grafik13.ru`;
* **SPF**: `v=spf1 a mx -all` в DNS;
* **DKIM** (`opendkim`) — подпись исходящих.

Без них письмо о подтверждении адреса человек, скорее всего, не увидит, и
регистрация не завершится.

### 6. Межсетевой экран и fail2ban

```bash
sudo cp /opt/grafik13/nftables.conf /etc/nftables.conf   # из репозитория
sudo nft -c -f /etc/nftables.conf                        # сначала проверить
sudo systemctl enable --now nftables

sudo cp fail2ban-jail.local /etc/fail2ban/jail.local
sudo systemctl enable --now fail2ban
sudo fail2ban-client status sshd
```

В наборе правил **нет** `flush ruleset` — это важно: общий сброс снёс бы
правила docker (проброс портов) и контейнеры молча перестали бы отвечать.
Своё хозяйство живёт в таблице `inet grafik`, и перечитывание файла
сбрасывает только её.

Если на сервере уже настроен `ufw` — используйте что-то одно. Два
межсетевых экрана хуже одного: правила складываются неочевидно, и однажды
отвалится то, что «точно разрешено».

### 7. nginx

Настройка сайта уже содержит блок для API (`location ^~ /api/`). После
обновления файла:

```bash
sudo cp nginx-site.conf /etc/nginx/sites-available/grafik13.ru
sudo cp nginx-security-headers.conf /etc/nginx/snippets/security-headers.conf
sudo nginx -t && sudo systemctl reload nginx
```

`nginx -t` — обязательно до перезагрузки: опечатка в прокси уронит и сайт.

### 8. Первая выкладка

В репозитории (Settings → Secrets and variables → Actions) к тем
переменным, которые уже настроены для сайта, добавляется одна:

| | Имя | Значение |
|---|---|---|
| Variable | `API_DEPLOY_ROOT` | `/opt/grafik13` (можно не задавать — это значение по умолчанию) |

Остальное (`SSH_HOST`, `SSH_USER`, `SSH_PRIVATE_KEY`, `SSH_KNOWN_HOSTS`,
`SSH_PORT`, `SITE_URL`) общее с выкладкой сайта.

Пользователь `SSH_USER` должен иметь право писать в `/opt/grafik13` и
запускать `docker` (группа `docker`).

Дальше — push в `main` (или запуск «API CD» руками с номером запуска
«API», у которого брать образ). Выкладка:

1. забирает образ, собранный и проверенный в CI, — второй сборки нет;
2. копирует рядом состав и скрипты обслуживания;
3. применяет миграции (`docker compose run --rm migrate`);
4. поднимает контейнер и **проверяет, что запущен именно новый образ**;
5. снаружи, через nginx, дёргает `/healthz`, `/readyz` и
   `/legal/documents`.

### 9. Расписания

```bash
sudo cp systemd/* /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now grafik-gc.timer grafik-backup.timer grafik-backup-verify.timer
systemctl list-timers 'grafik-*'
```

Юниты обновляются **руками**: выкладка копирует только скрипты и состав,
потому что перезагрузка демона и перезапуск таймеров — не её дело.

| Таймер | Когда | Что делает |
|---|---|---|
| `grafik-gc.timer` | 03:17 ± 15 мин | исполняет сроки хранения: надгробия (180 дней), версии (30), журнал событий (180), протухшие токены и ссылки, брошенные регистрации (30) |
| `grafik-backup.timer` | 02:40 ± 20 мин | резервная копия базы, шифрованная; хранит 30 дней |
| `grafik-backup-verify.timer` | 03:40 ± 10 мин | проверяет, что копия свежая, не пустая и зашифрована |

Сроки не косметика: они обещаны в политике и в карте данных
(`docs/legal/data-map.md`). Сборка мусора — это исполнение обещания, а не
уборка. Фактическая проверка («в базе действительно не осталось
просроченного») — запросом из `docs/legal/internal/09-vnutrenniy-kontrol.md`,
раз в квартал.

### 10. Проверки после установки

```bash
# контейнеры живы и здоровы
docker compose -f /opt/grafik13/compose.prod.yml ps

# приложение отвечает изнутри и снаружи
curl -s 127.0.0.1:8001/api/v1/healthz
curl -s https://grafik13.ru/api/v1/readyz

# в журнале одна строка — один JSON, и в нём нет ни адресов почты, ни блобов
docker compose -f /opt/grafik13/compose.prod.yml logs --tail 20 api

# база наружу не смотрит
ss -ltnp | grep -E '5432|8001'     # 8001 только на 127.0.0.1, 5432 — ничего

# почта из контейнера доходит до postfix
docker compose -f /opt/grafik13/compose.prod.yml exec api \
  python -c "import socket; socket.create_connection(('172.28.0.1', 25), 5); print('ок')"

# правила экрана применились
sudo nft list table inet grafik
```

## Обычная работа

### Выкладка

Push в `main` → workflow «API» (линтеры, типы, миграции вверх-вниз,
тесты, сборка образа) → workflow «API CD» (выкладка). Ничего делать не
надо.

### Откат

Тег работающего образа лежит в `/opt/grafik13/.env`, предыдущий — в
`.env.previous`:

```bash
cd /opt/grafik13
cat .env .env.previous
cp .env.previous .env
docker compose -f compose.prod.yml up -d api
```

Откат **не отменяет миграцию**. Если выпуск её содержал, сначала надо
понять, совместима ли прежняя версия кода с новой схемой: добавленный
столбец — да, удалённый или переименованный — нет. Поэтому миграции и
пишутся в два выпуска: сначала совместимое изменение схемы, потом
изменение кода.

### Журналы

```bash
docker compose -f /opt/grafik13/compose.prod.yml logs -f api
journalctl -u grafik-backup.service -n 50
journalctl -u grafik-gc.service -n 50
```

Журнал приложения — одна строка, один JSON. В нём **нет** адресов почты,
паролей, проверочных значений, ключей и блобов: человек в журнале
обозначен только `user_id`. Адрес обращения хранится отдельно — в таблице
`audit_log` в базе, 180 дней, по ч. 1 ст. 19 152-ФЗ.

Хранение журналов ограничено драйвером docker: пять файлов по 10 МиБ на
службу. Без этого ограничения журнал растёт, пока не кончится диск.

### Если что-то не так

| Признак | Почему чаще всего | Что делать |
|---|---|---|
| `502` на `/api/...`, сайт работает | контейнер `api` не поднялся | `docker compose logs api`; при слабом секрете приложение не стартует намеренно |
| `503` с `service_unavailable` | недоступна база или SMTP | `docker compose ps`, `journalctl -u postfix` |
| `/readyz` отвечает 503, `/healthz` — 200 | приложение живо, база нет | смотреть `postgres`: диск, журнал контейнера |
| в журнале адрес `172.28.0.1` вместо адреса человека | не задан `GRAFIK_TRUSTED_PROXIES` | вписать шлюз в `api.env`, перезапустить `api` |
| письма не приходят | postfix не принимает из контейнера или письма в спаме | `mynetworks`, 25-й порт в `nftables.conf`, записи PTR/SPF/DKIM |
| `429` у человека на ровном месте | предел обращений делится между процессами | `GRAFIK_WORKERS=1` (см. `core/limits.py`) |
| выкладка упала на «сервер не подготовлен» | нет `api.env` или `postgres.env` | шаг 4 этой инструкции |

## Резервные копии

### Как устроено

Раз в сутки `backup.sh` выгружает базу (`pg_dump --format=custom`) и
шифрует поток открытым ключом `age`. Готовый файл —
`/var/backups/grafik13/grafik13-ГГГГММДД-ЧЧММСС.dump.age`, права `400`,
срок хранения 30 дней (столько же обещано в политике: удаление аккаунта
догоняет копии в течение месяца).

Непрерывного архивирования (WAL) нет: база маленькая, а окно потери в
сутки допустимо — данные человека живут ещё и у него в браузере, сервер
это копия, а не источник истины.

**Копии надо унести с сервера.** Сервер и копии на одном диске — это
защита от «удалил не то», но не от «сервер пропал». Унести можно чем
угодно (`rsync` на свою машину, объектное хранилище в РФ): файл уже
зашифрован, и тому, кто его перевозит, доверять не нужно.

### Проверка раз в месяц — на своей машине

Автоматическая проверка на сервере отвечает только на вопрос «копия есть и
она зашифрована»: закрытого ключа там нет. Настоящая проверка делается
руками и там, где ключ есть:

```bash
# на своей машине
scp сервер:/var/backups/grafik13/grafik13-*.dump.age ./
GRAFIK_BACKUP_KEY=~/.config/grafik13/backup-key.txt \
  ./restore-check.sh grafik13-20261012-024000.dump.age
```

Скрипт расшифрует копию, поднимет одноразовый контейнер с PostgreSQL той
же версии, восстановит в него базу, проверит, что все таблицы на месте, и
покажет миграцию и число строк. После себя он не оставляет ни контейнера,
ни расшифрованного файла.

Числа строк смотреть обязательно: выгрузка одной схемы, без данных,
восстанавливается без единой ошибки — и выглядит как успех.

Без docker — то же самое в заранее созданную пустую базу:

```bash
createdb restore_check
GRAFIK_BACKUP_KEY=~/.config/grafik13/backup-key.txt \
GRAFIK_RESTORE_TARGET=postgresql://localhost/restore_check \
  ./restore-check.sh копия.dump.age
```

### Восстановление по-настоящему

Если сервера больше нет: поднять новый по инструкции выше до шага 8
включительно (контейнеры поднимутся с пустой базой), затем:

```bash
cd /opt/grafik13
docker compose -f compose.prod.yml stop api        # никто не пишет

# на СВОЕЙ машине расшифровать и привезти (на сервере ключа нет)
age -d -i ~/.config/grafik13/backup-key.txt копия.dump.age > db.dump
scp db.dump сервер:/tmp/

# на сервере
docker compose -f compose.prod.yml exec -T postgres \
  pg_restore --username=grafik --dbname=grafik --clean --if-exists \
             --no-owner --exit-on-error < /tmp/db.dump
rm -f /tmp/db.dump
docker compose -f compose.prod.yml start api
curl -s https://grafik13.ru/api/v1/readyz
```

И тот же `GRAFIK_PEPPER`, что был: с другим перцем база восстановится, а
войти не сможет никто.

## Чего здесь нет и почему

**Загона fail2ban для API.** Он читал бы журнал nginx с адресами — то
есть потребовал бы завести ещё одно хранилище персональных данных, которого
нет ни в карте данных, ни в политике. Перебор перекрыт в приложении:
предел обращений на вход — 10 попыток за 15 минут, отказ отвечает `429` с
`Retry-After`. Подробнее — в `fail2ban-jail.local`.

**Нескольких рабочих процессов.** `GRAFIK_WORKERS=1` не от бедности:
счётчик обращений живёт в памяти процесса, и при нескольких процессах
заявленный предел пришлось бы делить между ними. Работа у приложения почти
вся на ожидании базы, и асинхронный процесс справляется с ней весь.
Подробный разбор — в `api/src/grafik_api/core/limits.py`.

**Включённой синхронизации в сборке сайта.** Фронт собирается без неё
(`NEXT_PUBLIC_SYNC_ENABLED` не задан), поэтому на живом сайте нет ни
экрана входа, ни обращений к API. Включается она на шаге 15 — вместе с
опубликованными документами и уведомлением Роскомнадзора, не раньше: без
