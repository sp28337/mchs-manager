# Сервер синхронизации «График 1 3»

Бэкенд к приложению, которое считает рабочее время при графике «сутки через
трое». Его работа — хранить **зашифрованные на устройстве** копии профилей и
отдавать их на другие устройства того же человека. Содержимого он не видит:
ключ выводится из пароля в браузере и на сервер не уходит.

Что это значит для кода: сервер не умеет ни сливать правки, ни разрешать
конфликты — слияние делает браузер. Подробности и доводы:

* [`../docs/sync-contract.md`](../docs/sync-contract.md) — формат, ревизии,
  конфликты, лимиты, протокол;
* [`../docs/openapi-draft.yaml`](../docs/openapi-draft.yaml) — черновик описания
  API (настоящее собирает FastAPI из схем);
* [`../docs/legal/data-map.md`](../docs/legal/data-map.md) — какие данные
  обрабатываются и на каком основании. Данных, которых нет в карте, в базе быть
  не должно.

## Как поднять

Всё окружение сразу — из корня репозитория:

```bash
make up        # postgres + api + mailpit
make logs      # журналы API
make down      # остановить
```

API отвечает на `http://127.0.0.1:8000/api/v1/healthz`, письма видны на
`http://127.0.0.1:8025`, описание API при разработке — на `/docs`.

Без Docker (нужен свой postgres, когда дело дойдёт до базы):

```bash
make api-sync  # или: cd api && uv sync --locked
make api-run
```

## Как проверить

```bash
make api-check   # ruff + black --check + mypy + pytest с покрытием
make api-fmt     # отформатировать (black)
```

То же самое прогоняет CI — [`.github/workflows/api.yml`](../.github/workflows/api.yml),
и он же поднимает настоящую базу, гоняет миграции вверх-вниз-вверх,
проверяет расхождение схемы, собирает образ и дёргает `/healthz` внутри
контейнера.

**Тесты с базой и без.** Тестам, которым нужна база, адрес приходит в
`GRAFIK_TEST_DATABASE_URL`; без этой переменной они пропускаются, а
остальные идут как есть — так проверку можно гонять и без поднятого
окружения:

```bash
make api-test                                              # без базы
GRAFIK_TEST_DATABASE_URL=postgresql+psycopg://grafik:grafik@127.0.0.1:5432/grafik \
  make api-test                                            # с базой
```

Контур описан в `tests/conftest.py`: схема поднимается миграциями один раз
на прогон, каждый тест живёт в своей транзакции с безусловным откатом, а
сессии приложения привязаны к тому же соединению в режиме точек
сохранения — поэтому ручка честно вызывает `commit()`, а база после теста
остаётся прежней. Фабрики данных — в `tests/factories.py`.

## База и миграции

PostgreSQL, SQLAlchemy в асинхронном режиме (psycopg 3), Alembic. Один
драйвер и для приложения, и для миграций: две разные строки подключения
означали бы два разных поведения.

```bash
make up            # поднимает базу вместе с остальным
make api-migrate   # применить миграции
make api-drift     # не разошлись ли модели с базой
make api-revision m="что сделано"
```

Миграции при старте контейнера не применяются намеренно: в бою это делает
отдельный шаг выкладки (шаг 13), иначе два одновременно поднятых процесса
начнут менять схему разом. При разработке — руками, командой выше.

Таблицы и почему они такие — в докстрингах `grafik_api/models/*`, перечень
данных и оснований обработки — в [`../docs/legal/data-map.md`](../docs/legal/data-map.md).
Двух решений, которые отличаются от первоначального плана, стоит держаться:

* **солей в базе нет** — они выводятся из нормализованного адреса почты;
* **таблицы надгробий нет** — надгробие это состояние элемента (`deleted_at`
  и новая ревизия), так выборка изменений остаётся одним запросом.

Правила про миграции — в [`migrations/README.md`](migrations/README.md).

## Вход и сессии

Пароль на сервер не приходит. Браузер считает из него один argon2id
(64 МиБ, три прохода) и берёт из результата два разных значения через
HKDF: ключ обёртки (`KEK`) и проверочное значение (`verifier`). На сервер
уходит только второе, и даже оно хранится как
`argon2id(HMAC-SHA256(перец, verifier))`. Перец — в окружении, а не в
базе: украденной базы не должно хватать для подбора.

Серверный argon2 скромнее браузерного (19 МиБ против 64) намеренно: на
вход ему подаётся не пароль, а результат браузерного argon2id, то есть
подбор и так стоит 64 МиБ за попытку. Браузерная половина схемы — в
[`../src/features/sync/crypto/`](../src/features/sync/crypto/), её
векторы — в [`../docs/crypto-vectors.json`](../docs/crypto-vectors.json),
и сходимость двух реализаций проверяет `tests/test_crypto_contract.py`.

| Что | Где живёт | Сколько |
|---|---|---|
| access-токен (JWT) | в памяти вкладки | 15 минут |
| refresh-токен | cookie `HttpOnly; Secure; SameSite=Strict; Path=/api/v1/auth` | 30 дней, ротация при каждом обновлении |
| обёртки ключа данных | база, зашифрованные | до удаления аккаунта |

Токены живут семьями: каждое обновление выдаёт новый и помечает прежний
использованным. Предъявленный дважды токен означает утечку копии — тогда
гасится вся семья, и войти заново придётся обоим, и хозяину, и вору.

**Что уже работает:** `POST /auth/params`, `/auth/register`, `/auth/login`,
`/auth/refresh`, `/auth/logout`, `/auth/verify-email`, `/auth/recover/start`,
`/auth/recover/finish`.

## Письма

Писем два вида, оба служебные: ссылка подтверждения адреса (уходит при
регистрации) и ссылка восстановления доступа. Рассылок нет и не будет — на
них нужно отдельное согласие, которого мы не просим.

Отправляет их **свой SMTP на том же сервере**: внешний отправщик стал бы
вторым обработчиком персональных данных, которого пришлось бы называть в
уведомлении РКН и с которым нужен договор поручения (раздел 4
[`../docs/legal/data-map.md`](../docs/legal/data-map.md)). При разработке
письма ловит `mailpit` и показывает на `http://127.0.0.1:8025`. Если
`GRAFIK_SMTP_HOST` пуст, письма не отправляются вовсе и остаётся запись в
журнале — так приложение поднимается там, где почты нет.

В письме только ссылка с одноразовым токеном: ни пароля, ни ключа
восстановления, ни содержимого графика у сервера и нет. Токен живёт сутки,
срабатывает один раз, в базе лежит его `sha256`, и назначения не
взаимозаменяемы — ссылкой подтверждения пароль не сменить.

Это единственное место, где токен существует: в ответе ручки его нет. В
тестах отправщик подменяется (`tests/factories.Почта`, фикстура `почта`),
и письмо читается из списка — иначе ни подтверждение адреса, ни
восстановление доступа не проверить.

## Права субъекта и смена пароля

Три ручки из четырёх — права человека по 152-ФЗ, а не удобства, и поэтому
работают сразу, без переписки с оператором:

| Ручка | Что делает | Право |
|---|---|---|
| `GET /account` | что сервер знает об аккаунте, включая версии согласий | ст. 14 |
| `GET /account/export` | один JSON со всем: аккаунт, согласия, журнал входов, элементы | ст. 14 |
| `DELETE /account` | уничтожает всё | ч. 2 ст. 9, ст. 21 |
| `POST /account/password` | смена пароля | — |

**Отдельной ручки отзыва согласия нет намеренно:** без адреса почты и
обёрток ключа аккаунта не существует, поэтому отзыв — это и есть удаление.
Так сказано и в политике, и в тексте согласия.

**Удаление уничтожает всё:** блобы, историю, обёртки ключей, адрес почты,
согласия, сессии, журнал входов. Остаётся одна обезличенная строка аудита —
«аккаунт `<uuid>` удалён» с тремя счётчиками, — ею оператор подтверждает,
что удаление исполнено; определить по ней человека нельзя, адреса в базе
уже нет. Резервные копии догоняют удаление по своему сроку (30 дней), и в
политике это сказано прямо.

**Смена пароля не перешифровывает данные:** пароль шифрует обёртку ключа
данных, а не сами данные, поэтому меняются тридцать два байта. Новую
обёртку присылает браузер — сервер ключа не видит. Прочие сессии при этом
гаснут, кроме той, с которой меняли (`X-Device-Id`): если пароль меняют
из-за того, что его узнали, чужая сессия не должна его пережить.

Удаление и смена пароля спрашивают проверочное значение ещё раз: украденного
access-токена не должно хватать, чтобы стереть человеку год работы. Неудачная
попытка попадает в журнал событий безопасности и **переживает отказ** —
запись фиксируется до того, как ручка ответит `401`.

## Синхронизация

Единица обмена — элемент: указатель библиотеки (`index`, один на аккаунт) и
профиль (`profile`, по одному на запись проводника). Сервер видит байты,
размер и ревизию — и больше ничего.

```
GET  /api/v1/sync?since=0&limit=50   что изменилось после ревизии
POST /api/v1/sync                    отправить правки (до 50 за раз)
```

Ревизия — одна последовательность на аккаунт, а не на элемент: курсор
выборки это одно число. Отправка начинается с блокировки строки аккаунта,
чтобы два устройства, отправившие правки разом, не получили один номер.

**Расхождение — не ошибка.** `POST /sync` отвечает `200` и приносит и
принятые элементы, и нынешнее состояние тех, чья базовая ревизия не
совпала. Клиент сливает их у себя (трёхсторонней сверкой `base ↔ local ↔
remote`) и отправляет снова. Отвергать всю отправку из-за одного профиля
нельзя: остальные девять тогда не доедут.

**Повтор той же правки** (`mutation_id`) не создаёт новой ревизии: сеть
рвётся, клиент повторяет, и дважды записанная правка выглядела бы
конфликтом с самим собой.

**Удаление** — надгробие: элемент остаётся своей строкой с новой ревизией,
но содержимое и история стираются. Надгробия живут 180 дней — столько у
редко включаемого устройства есть, чтобы узнать об удалении. Когда сборщик
их убирает, он поднимает `min_rev_available`, и устройство с курсором
старше получает `resync_required` — «выбери всё с нуля» вместо тихой
потери.

Сборщик (`SyncService.collect_garbage`) написан и проверен тестами, но по
расписанию пока не запускается — это шаг 13.

## Журналы

Одна запись — одна строка JSON, вывод только в stdout (`core/logging.py`).
Смотреть удобно через `jq`:

```bash
make logs | jq 'select(.event == "http.access")'          # запросы
make logs | jq 'select(.request_id == "7b02f6b4…")'       # всё об одном запросе
make logs | jq 'select(.level == "ERROR")'
```

У каждой записи есть `request_id` — по нему собирается вся обработка одного
запроса, даже когда запросов много и они идут вперемешку. Клиентский
`X-Request-Id` принимается, если годный, и всегда возвращается в ответе.

Чего в журналах нет и быть не должно: адресов почты, паролей, проверочных
значений, ключей, обёрток, блобов, ключей восстановления и строк запроса.
Человек в журнале — это `user_id` (uuid). `SensitiveDataFormatter` замазывает
то, что всё-таки просочилось, но это последняя линия обороны, а не защита:
правило — не передавать чувствительное в журнал.

Уровень задаётся `GRAFIK_LOG_LEVEL` (в compose для разработки — `DEBUG`, в
нём видно ещё и строку «запрос начат»).

## Версии Python

В образе и в CI — **3.14**. В `pyproject.toml` стоит `requires-python = ">=3.13"`,
и это не небрежность: в контейнере, где пишется код, закрыт доступ к
`github.com`, откуда uv тянет управляемые интерпретаторы, и на 3.14 там не
собрать окружение вовсе. Синтаксиса, которого нет в 3.13, в коде нет —
за этим следит ruff (`target-version = "py313"`).

## Раскладка

```
src/grafik_api/
  main.py          сборка приложения: настройки, жизненный цикл, роутеры
  core/            настройки, журналирование, ошибки, крипто — ни от кого не зависит
  api/             ручки: HTTP и только HTTP; зависимости — в api/deps.py
  services/        правила: вызываются из теста без HTTP
  repositories/    запросы к базе: без бизнес-правил
  models/          таблицы SQLAlchemy
  schemas/         то, что приходит и уходит по HTTP
  db/              движок, фабрика сессий, базовый класс
  middleware/      request_id и запись доступа
tests/
```

Слои однонаправленные: `api → services → repositories → models`. Ручка не
трогает сессию базы напрямую, сервис не знает про `Request`, репозиторий не
решает, законна ли операция. Правило каждого слоя записано в его
`__init__.py` — там, где его и нарушают.

Пустых модулей «на будущее» здесь нет: файл появляется на том шаге, которому
он нужен. Что когда — в докстрингах слоёв.
